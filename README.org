#+TITLE: Sandboxed LLM Agent Stack
#+OPTIONS: toc:2 num:nil
#+STARTUP: overview

One isolated virtual machine per project, on your own machine. ~agent claude-api
myproject~ gives a coding agent a full Arch toolchain, that one project's files
and nothing else of yours, network access that is filtered and logged, and web
search through a service you run yourself. The sandbox is disposable:
~agent reset~ throws away everything done inside it and starts it again from
the current golden image.

Everything site-local — paths, sizing, which agents, which credentials, which
services — lives in one short file, ~site.nix~, in a folder of your own. This
repository holds the stack, never your settings.

* How it fits together

Three layers, each holding the one above it at arm's length.

| Layer | What it is                                       | What lives there                          |
|-------+--------------------------------------------------+-------------------------------------------|
| L0    | your own machine                                 | your site folder, your secrets, your      |
|       |                                                  | project files, and the golden image build |
| L1    | one libvirt VM, /the carrier/: NixOS, built      | the filtering policy, the logs, and the   |
|       | from this flake                                  | state that has to survive                 |
| L2    | one nested VM per project, /the sandbox/: Arch,  | an agent, and a single project's files    |
|       | built by mkosi                                   |                                           |

Every sandbox is cloned from one shared golden image onto a copy-on-write
overlay, and gets its own user id, its own point-to-point network link, and its
own project directory passed through from L0. Service stacks — the search
engine an agent queries, for instance — run as containers on L1 itself.

The design rule is that *nothing downstream opens a connection upstream*, and
what L1 enforces of it today is precise rather than complete. Everything a
sandbox sends passes through L1 and is recorded there: web traffic through its
proxy, names through its resolver, every other connection in a flow log. L1
refuses a sandbox's direct connections to other sandboxes, to the network
between L0 and L1, and to the service containers, and its own ssh is reachable
from L0 alone. It does not yet refuse your LAN, and its proxy will fetch web
pages from private addresses, L0's included — see
[[*What a sandbox can and cannot reach][What a sandbox can and cannot reach]]
before relying on it.

* Requirements on L0

L0 must be x86_64, with hardware virtualization enabled in firmware and nested
virtualization available — the sandboxes are VMs inside a VM, so without
nesting nothing past the carrier works.

*Arch is the tested host.* The stack was built and is run on it daily. Ubuntu
24.04 is documented here from the code and the distributions' own
documentation, but has not been run end to end. The open questions are listed
at the end of this section rather than buried, because someone picking this up
needs to know which instructions are proven and which are reasoned.

*On Ubuntu, read [[*Open questions on Ubuntu 24.04][Open questions on Ubuntu
24.04]] before running anything.* One of them is likely to stop the image build
outright, and knowing that in advance turns a confusing failure into an
expected one.

Do this section first, then [[*Quickstart][Quickstart]] takes it from there.

binary the image build cannot do without is ~pacman~: mkosi sets ~PATH~ to
~/usr/bin:/usr/sbin~ inside its own sandbox and looks for it there.

** Arch

#+BEGIN_SRC sh
sudo pacman -S --needed libvirt qemu-full virtiofsd dnsmasq nix \
                        mtools base-devel git curl openssh tigervnc
sudo systemctl enable --now libvirtd.socket nix-daemon.socket
#+END_SRC

The Arch package ships no ~/nix~ directory. The daemon's socket directory
comes from ~/usr/lib/tmpfiles.d/nix-daemon.conf~, which pacman applies in a
post-transaction hook that does not always fire; ~/nix/store~ itself is created
by the daemon the first time it runs. Applying the file again is harmless, so
do it either way, then let the daemon create the store:

#+BEGIN_SRC sh
sudo systemd-tmpfiles --create /usr/lib/tmpfiles.d/nix-daemon.conf
nix store info                                # starts the daemon, which creates the store
ls -ld /nix/store
#+END_SRC

Nix from the Arch package needs its daemon running, and the client needs to be
told to use it. Without that, ~nix build~ tries to create ~/nix/store~ itself
and fails on permissions. Arch ships the environment snippet in
~/etc/profile.d/~, which an interactive non-login zsh never sources, so the
variable usually has to be set by hand. Nix also needs flakes turned on:

#+BEGIN_SRC sh
echo 'export NIX_REMOTE=daemon' >> ~/.zshrc      # or ~/.bashrc
export NIX_REMOTE=daemon

mkdir -p ~/.config/nix
echo 'experimental-features = nix-command flakes' >> ~/.config/nix/nix.conf
#+END_SRC

*No group membership is required on Arch*, which is worth saying because so
much virtualization documentation assumes otherwise:

- ~/dev/kvm~ is mode 0666, set by systemd's own udev rule, so there is nothing
  to join in order to use KVM.
- There is no ~nix-users~ group on Arch unless something created one: the
  daemon socket directory is world-accessible by default.
- ~virsh~ is always run under ~sudo~ here. ~install~ and ~deploy~ re-execute
  themselves under ~sudo~, and ~golden-build~, which must run as your own user,
  calls ~sudo~ for the steps that need it, so the ~libvirt~ group buys nothing. Join it if you prefer to drop the ~sudo~ from
  your own ~virsh~ habits; nothing here depends on it.

Checks, none of which change anything:

#+BEGIN_SRC sh
ls -l /dev/kvm                                # expect crw-rw-rw-
cat /sys/module/kvm_intel/parameters/nested   # or kvm_amd — Y or 1, either is on
nix store info                                # should report the daemon store
#+END_SRC

** Ubuntu 24.04 LTS

~virtiofsd~, ~pacman-package-manager~, ~makepkg~, ~archlinux-keyring~ and
~tigervnc-viewer~ are all in *universe*, so enable it first.

#+BEGIN_SRC sh
sudo add-apt-repository universe
sudo apt update
sudo apt install --no-install-recommends \
     libvirt-daemon-system libvirt-clients qemu-system-x86 qemu-utils \
     virtiofsd dnsmasq-base mtools build-essential git curl openssh-client \
     pacman-package-manager makepkg archlinux-keyring tigervnc-viewer
sudo systemctl enable --now libvirtd.socket
#+END_SRC

Ubuntu has no usable Nix package, so take it from upstream. The ~--daemon~
form is the multi-user install, which is what the Arch instructions above
arrive at by a different route; it writes its own profile snippet and systemd
unit, so ~NIX_REMOTE~ needs no setting by hand.

#+BEGIN_SRC sh
sh <(curl -L https://nixos.org/nix/install) --daemon
# open a new shell, then:
mkdir -p ~/.config/nix
echo 'experimental-features = nix-command flakes' >> ~/.config/nix/nix.conf
nix store info
#+END_SRC

*Unlike Arch, Ubuntu probably does need the ~kvm~ group.* Debian and Ubuntu
have long shipped a udev rule with QEMU setting ~/dev/kvm~ to 0660 root:kvm,
where Arch leaves systemd's 0666 in place. Check before assuming either way:

#+BEGIN_SRC sh
ls -l /dev/kvm                                # 0666 -> nothing to do
sudo usermod -aG kvm "$USER"                  # only if it is 0660; then log out and back in
cat /sys/module/kvm_intel/parameters/nested   # or kvm_amd — Y or 1, either is on
#+END_SRC

** libvirt and virtiofsd

Applies to both distributions. This design has virtiofsd running as *root* so
that files an agent creates keep uid 1000 across the hop to L0. libvirt
launches virtiofsd as the same user it launches QEMU as, which is
~libvirt-qemu~ on both Arch and Ubuntu.

Rather than change ~/etc/libvirt/qemu.conf~, which would move every VM on the
host, the domain XML carries a per-domain DAC label:

#+BEGIN_SRC xml
<seclabel type='static' model='dac' relabel='no'>
  <label>+0:+0</label>
</seclabel>
#+END_SRC

So nothing needs configuring. It is worth confirming once, with L1 running,
that it took:

#+BEGIN_SRC sh
ps -o user=,args= -C virtiofsd    # expect root
ps -o user= -p "$(pgrep -f 'guest=agent-l1' | head -1)"
#+END_SRC

The domain also names its own virtiofsd binaries: two-line wrappers in the Nix
store that run the flake's pinned virtiofsd, the one the sandboxes get on L1,
with ~--inode-file-handles=never~, and for the dotfiles export with
~--readonly~ as well. Both hops need the first flag: with file handles on L0, a
deleted file on L0's disk is freed at once and its inode number reused, while
L1's virtiofsd, which tells files apart by inode number, may still refer to it;
a sandbox then sees ~Bad file descriptor~ or ~Stale file handle~ under churn
such as git's. ~install~ and ~deploy~ keep the wrappers alive with one GC root
each, ~/nix/var/nix/gcroots/agent-stack-virtiofsd~ and
~agent-stack-virtiofsd-readonly~ beside it, so ~nix-collect-garbage~ on L0 is
safe. The ~ps~ line above should show a ~/nix/store/…-virtiofsd-…~ binary with
~--inode-file-handles=never~ on both of L1's exports, and ~--readonly~ on the
dotfiles one.

** Open questions on Ubuntu 24.04

Six things that could not be settled without running it. Each is listed with
what would go wrong and what to try, so a first run is diagnosis rather than
guesswork. Please record the answers here as they are found.

*1. Unprivileged user namespaces are restricted by AppArmor.* This is the one
most likely to stop the image build outright. mkosi sandboxes itself with
bubblewrap, and on Ubuntu 24.04 that fails with ~bwrap: setting up uid map:
Permission denied~. The usual fix is an AppArmor profile naming
~/usr/bin/bwrap~ — but mkosi here comes from the flake, so its bubblewrap lives
under ~/nix/store~ and no profile keyed to the Ubuntu path will match it.
Ubuntu's own documented escape hatch is to turn the restriction off:

#+BEGIN_SRC sh
echo 'kernel.apparmor_restrict_unprivileged_userns=0' \
  | sudo tee /etc/sysctl.d/60-apparmor-namespace.conf
sudo reboot
#+END_SRC

That weakens a kernel hardening measure host-wide, so it is worth confirming
the build actually fails first. The alternatives are a profile written against
the current store path, which breaks whenever nixpkgs moves, or building the
golden inside an Arch container and skipping the question.

*2. ~pacman~ is old.* Ubuntu 24.04 ships 6.0.2; Arch is on the 7 series.
Whether that version can read today's Arch repositories, and write a package
database the image can use, is unknown. If it cannot, the options are the
newer ~pacman~ from a later Ubuntu release, or an Arch container for the image
build.

*3. The ~archlinux-keyring~ package dates from March 2024.* Packages signed by
packagers whose keys were added since will fail verification. mkosi fetches
distribution keys remotely by default *on Ubuntu hosts specifically*, which
sidesteps this — but recent mkosi also prefers the host's pacman keyring for
Arch images, and which behaviour wins depends on the pinned version. If
signature errors appear, initialise the host keyring:

#+BEGIN_SRC sh
sudo pacman-key --init
sudo pacman-key --populate archlinux
#+END_SRC

*4. ~makepkg --syncdeps~ calls ~pacman~ to install build dependencies*, and on
Ubuntu there are no Arch repositories configured for it to install from.
~yay-bin~ repackages a prebuilt binary and should not care; ~emacs-lsp-booster~
compiles from source and needs Rust. Both are always built, whatever
~site.nix~ says. Options: install the build dependencies with ~apt~ and remove
~--syncdeps~ from ~golden-build~ in a clone of the stack — see
[[*Working on the stack itself][Working on the stack itself]]; keep anything you
add to ~guest.aurPackages~ to ~-bin~ variants; or build the golden in an Arch
container.

*5. AppArmor confines libvirt on Ubuntu*, generating a profile per domain.
Two things here may trip it: the per-domain root DAC label above, and the
~l1-system-current.qcow2~ symlink, which a generated profile may not follow.
If the domain refuses to start after an image swap, add the paths under
~/etc/apparmor.d/local/abstractions/libvirt-qemu~. Pointing ~<source file=…>~
at the dated image with ~sudo virsh edit~ also works, but only until the next
~install~ or ~deploy~, which redefine the domain from the flake.

*6. virtiofsd's install path differs.* Debian and Ubuntu place it under
~/usr/libexec~ rather than ~/usr/bin~. libvirt normally finds it either way,
but if the workspace mount is empty this is worth ruling out:

#+BEGIN_SRC sh
ls -l /usr/libexec/virtiofsd /usr/lib/qemu/virtiofsd /usr/bin/virtiofsd 2>/dev/null
#+END_SRC

A seventh possibility, if several of these turn out to be real: run
~golden-build~ inside an Arch container and leave the rest of the stack on
Ubuntu. It answers 1 through 4 at once, at the cost of a container runtime on
L0. Nothing outside the golden image build depends on the host being Arch.

* Quickstart

With the host packages from the previous section installed, these six steps go
from there to an agent running in its own VM. Each has a section of its own
further down.

*Every ~nix run~, ~nix build~ and ~nix profile~ command in this README runs
from your site folder*, the one step 1 creates. It is a plain folder holding
your settings, and nothing in it needs Git.

*1. Create your site folder.*

#+BEGIN_SRC sh
mkdir ~/agent-site && cd ~/agent-site
nix flake init -t github:mclbn/agent-stack
#+END_SRC

This writes ~flake.nix~, which you leave alone, and ~site.nix~, which is yours.
A ~flake.lock~ appears with the first command below: it pins the version of
the stack you are running.

*2. Make the folders and the key.* The export root holds your projects, one
sub-folder each, and is the only part of L0 that L1 can see.

#+BEGIN_SRC sh
mkdir -p ~/work/demo && chmod 700 ~/work     # demo: a project to start with
mkdir -p ~/agent-dotfiles                    # copied into every new sandbox
ssh-keygen -t ed25519 -f ~/.ssh/agent-stack -C agent-stack
cat ~/.ssh/agent-stack.pub                   # the line step 3 needs
#+END_SRC

*3. Edit ~site.nix~.* Replace the three values containing ~CHANGEME~, the whole
quoted text each time, with your own. Keep the rest of the file: everything in
it sits between its first ~{~ and its last ~}~.

#+BEGIN_SRC nix
{
  exportRoot = "/home/alice/work";
  dotfilesRoot = "/home/alice/agent-dotfiles";
  operatorSshKey = "ssh-ed25519 AAAAC3Nz... agent-stack";   # the whole line cat printed
  ...
}
#+END_SRC

Then choose ~profile~ in the ~guest~ block, now rather than later. ~"light"~
builds in minutes and has no Emacs, no VNC desktop and no TeX; ~"full"~ has all
three and takes around 20 GB. Switching afterwards means building the image
again. Every other setting is in the file too, commented out at its default —
see [[*Settings][Settings]] — and a leftover ~CHANGEME~ or a mistyped name stops
the next command with an error naming it.

*4. Build and start the carrier*, the L1 VM that holds everything else.

#+BEGIN_SRC sh
nix run '.#ssh-config' >> ~/.ssh/config   # once: how ssh reaches L1 and the sandboxes
nix build '.#image'                       # optional, install builds it too: ~10 min, in a VM
nix run '.#install'                       # asks for sudo: disks, network, the VM
ssh l1 true && echo "carrier reachable"   # give it a minute; answer yes to its key once
#+END_SRC

*5. Build the golden image*, the Arch image every sandbox is cloned from:
minutes for ~light~, tens of minutes for ~full~.

#+BEGIN_SRC sh
nix run '.#golden-build'
#+END_SRC

*6. Install the wrapper and start a sandbox.* The first ~agent~ command for a
project creates it.

#+BEGIN_SRC sh
nix profile install '.#agent'
agent shell demo           # ctrl-b d to detach, leaving it running
#+END_SRC

Inside, ~/work~ is ~~/work/demo~ from L0, a file you create there appears on L0
owned by uid 1000 — you, on a single-user machine — and
~curl https://example.com~ leaves through L1's proxy and shows up in its log.

~agent shell~ needs no credentials; an agent needs its API key. Uncomment the
~credentials.entries~ block in ~site.nix~, keeping the entries for the agents
you use, check that each command prints its key — see
[[*Credentials][Credentials]] — and then:

#+BEGIN_SRC sh
nix profile upgrade agent
agent claude-api demo
#+END_SRC

Keep the site folder with your backups: it is all that makes this installation
yours. Moving to a newer stack later is [[*Upgrade the stack][one command]].

* Settings

~site.nix~ lists every setting. The three required ones and ~guest.profile~
and ~guest.snapshot~ are set; every other line is commented out and shows the
default, which applies as long as the line stays commented — a later version
of the stack may change it. To change a setting, remove the ~#~ at the start
of its line and edit the value. What each setting does, in full, is in
[[file:site/options.nix][site/options.nix]], online at
https://github.com/mclbn/agent-stack/blob/main/site/options.nix. A
~site.nix~ with a few settings changed looks like this:

#+BEGIN_SRC nix
{
  exportRoot = "/home/alice/work";
  dotfilesRoot = "/home/alice/agent-dotfiles";
  operatorSshKey = "ssh-ed25519 AAAAC3Nz... agent-stack";

  timezone = "Europe/Paris";              # L1 and the sandboxes, like L0

  guest = {
    profile = "full";
    snapshot = "2026/09/27";
    extraPackages = [ "htop" ];
  };

  sandbox.memoryMiB = 8192;               # a dot is short for a block of one
  serviceStacks.searxng.enable = false;
}
#+END_SRC

Four things worth knowing:

- *A list you set replaces the default list.* To add an agent to
  ~guest.agentInstallers~, uncomment the whole list and add to it. The lists
  meant for additions, ~guest.extraPackages~ and ~guest.aurPackages~, start
  empty.
- *A setting is written once.* Inside the ~guest~ block it is ~profile~;
  outside it, ~guest.profile~. Writing it both ways fails with
  ~attribute 'guest.profile' already defined~.
- *Every name and value is checked.* ~timzone~ fails with
  ~The option `timzone' does not exist~, and suggests ~timezone~;
  ~profile = "lite"~ fails with the values it accepts.
- *To see a value in effect*, defaults included:
  ~nix eval '.#site.timezone'~.

** Everything else, and what to re-run

Grouped by what a change costs, which is the only thing you need to know at the
moment you make one. ~deploy~ restarts L1, so every running sandbox stops with
it; start them again with ~agent start~ once ~ssh l1 true~ answers.

| Settings                                            | After changing them                    |
|-----------------------------------------------------+----------------------------------------|
| ~credentials.*~                                     | ~nix profile upgrade agent~. Nothing   |
|                                                     | rebuilds; the new value appears at the |
|                                                     | next attach.                           |
| ~logging.*~, ~serviceStacks~,                       | ~nix run '.#deploy'~                   |
| ~sandbox.memoryMiB~, ~sandbox.vcpu~,                |                                        |
| ~carrier.extraModules~                              |                                        |
| ~dns.*~, ~ntp.*~                                    | ~nixos-rebuild … switch~ — in place,   |
|                                                     | about fifteen seconds, no reboot and   |
|                                                     | no image swap; ~deploy~ works too.     |
|                                                     | See [[*Change how DNS is resolved][Change how DNS is resolved]].        |
| ~exportRoot~, ~dotfilesRoot~, ~operatorSshKey~,     | ~nix run '.#deploy'~, which redefines  |
| ~l1.memoryMiB~, ~l1.vcpu~, ~l1.cpuQuota~,           | the libvirt domain as well as          |
| ~l1.cpuPeriod~, ~l1.systemDiskMiB~                  | replacing the system disk. Create a    |
|                                                     | new ~exportRoot~ or ~dotfilesRoot~     |
|                                                     | first: only ~install~ checks for it.   |
| ~guest.*~ — locale, keymap, profile,                | ~nix run '.#golden-build'~, then       |
| snapshot, vnc, extraPackages, aurPackages,          | ~agent reset~ on each project, since   |
| agentInstallers                                     | each one stays on the golden it was    |
|                                                     | created from. ~guest.locale~ also      |
|                                                     | needs ~nix profile upgrade agent~.     |
| ~timezone~                                          | ~deploy~ for L1, and ~golden-build~    |
|                                                     | with a reset per project for the       |
|                                                     | sandboxes                              |
| ~sshIdentityFile~                                   | ~nix run '.#ssh-config'~ again, in     |
|                                                     | place of the old stanzas in            |
|                                                     | ~~/.ssh/config~                        |
| ~imageDir~, ~domainName~, ~domainUuid~,             | Not a plain re-run: ~install~ leaves   |
| ~networkName~, ~bridgeName~                         | an existing domain, network and data   |
|                                                     | disk where they are. See below.        |

Two notes on that table. A ~sandbox.*~ change reaches a project only when it is
next started; after the ~deploy~ it needs, every project is stopped already,
so ~agent start~ is enough. And adding to ~guest.aurPackages~ builds the
package but does not install it: the package name also has to be in
~guest.extraPackages~.

Changing ~wan.*~, ~networkName~ or ~bridgeName~ means stopping L1 and removing
the old network first, because ~install~ leaves an existing network alone and
does not restart a running L1. L1's address is in the ssh stanzas too, and its
host key is recorded under the old one:

#+BEGIN_SRC sh
sudo virsh shutdown agent-l1
sudo virsh net-destroy agent-wan
sudo virsh net-undefine agent-wan
nix run '.#install'                        # defines the new network, starts L1
nix run '.#ssh-config'                     # replaces the old stanzas in ~/.ssh/config
ssh-keygen -R 10.99.0.2                    # the old address, if wan.address changed
#+END_SRC

Changing ~domainName~ or ~domainUuid~ means undefining the old domain first
(~sudo virsh shutdown agent-l1~, then ~sudo virsh undefine agent-l1~), since
libvirt refuses a second one with the same name or UUID. Changing ~imageDir~
means moving the disks: ~install~ creates a new, empty data disk in a
directory that has none, and L1 would boot with an empty ~/data~ — every
overlay, golden, log and allocation would be left behind in the old directory.
Shut L1 down, ~sudo mv~ the old directory to the new path, then
~nix run '.#install'~. In all three commands above, substitute your own names
if you changed them.

** Day to day

*** Start L1 after a host reboot

L1 is defined as a libvirt domain but does not start on its own, so after a
host reboot nothing works until it is up: ~agent~ talks to L1 over ssh and
fails at the first command without it. ~/data~ — overlays, logs, configuration
— is untouched by a reboot.

#+BEGIN_SRC sh
sudo virsh start agent-l1              # this boot
sudo virsh autostart agent-l1          # once, then every boot from now on
#+END_SRC

The two are not alternatives: ~start~ powers it on now, ~autostart~ records a
preference libvirt acts on at every host boot and does nothing to the machine
today. Set autostart once and the command above stops being something you have
to remember. ~sudo virsh autostart --disable agent-l1~ undoes it.

~ssh l1 true~ answers once it is ready.

~nix run '.#deploy'~ also leaves L1 running, which makes it a tempting habit,
but it builds and installs a new system image and replaces L1's system disk
with it. It is for a changed carrier configuration, not for turning the machine
on — see [[*Changing the carrier configuration][Changing the carrier configuration]].

*** Is everything healthy?

Five layers to confirm, cheapest first. A failure at any line makes the lines
below it meaningless, so read the output in order.

#+BEGIN_SRC sh
sudo virsh list --all                  # agent-l1 running
sudo virsh net-list                    # agent-wan active
ssh l1 true && echo "carrier reachable"
ssh l1 'systemctl is-system-running'   # running, or degraded + what failed
ssh l1 'systemctl list-units "svc-*" --no-pager'   # the service stacks
ssh l1 agentctl status                 # every project: address, state, overlay, image
ssh l1 'btrfs filesystem usage -h /data | head -4'
#+END_SRC

~degraded~ is the one worth reading closely: the carrier is up and a unit has
failed, which ~systemctl --failed~ names. ~agentctl status~ reports ~running~,
~stopped~ or ~reset~ per project, so a project you expected to be up and which
reads ~reset~ has lost its overlay rather than its power. Its last column reads
~missing~ when the project's workspace is gone from L0, which makes it a
candidate for ~agent delete~, and ~?~ when the export is not mounted on L1 and
there is no way to tell.

*Untested.* Assembled from checks that are individually proven; the sequence
has not been run as one block.

*** Start, stop, reset or delete a sandbox

~stop~ keeps the overlay, ~reset~ discards it, ~delete~ discards the project —
see [[*Sandboxes][Sandboxes]] and [[*Delete a project][Delete a project]].

#+BEGIN_SRC sh
agent list                             # every project, its address and state
agent start demo                       # up, credentials pushed, no attach
agent stop demo                        # power off, overlay intact
agent reset demo                       # stop, then delete the overlay
agent delete demo                      # reset, then free its config and address
agent prune                            # free goldens that no overlay uses any more
#+END_SRC

Only starting creates a project. ~stop~, ~reset~, ~delete~ and ~capture~ on a
name that was never started, or has been deleted, fail with ~no project~ rather
than allocating an address for a typo.

*** Attach an agent

Each verb is one agent in one project, in tmux so a dropped connection does not
kill the run — see [[*The agent wrapper][The agent wrapper]]. The sandbox is
created and started if it is not already up.

#+BEGIN_SRC sh
agent claude-api demo                  # Claude Code, API key
agent claude-pro demo                  # Claude Code, Pro auth
agent codex demo                       # Codex CLI, API key
agent opencode demo                    # opencode
agent shell demo                       # a plain shell, no credentials needed
#+END_SRC

~ctrl-b d~ detaches and leaves it running. Credentials are pushed on every
attach and cleared by ~agent stop~, so a missing key is a ~site.nix~ question
rather than a sandbox one — see [[*Credentials][Credentials]].

*** Emacs, or just the viewer

*Full profile only*: a light golden has no display stack and both commands
refuse by name — see [[*The display, and Emacs][The display, and Emacs]].

#+BEGIN_SRC sh
agent emacs demo                       # a frame, and a viewer on it
agent vnc demo                         # just the viewer on the sandbox's display
#+END_SRC

The Emacs daemon lives as long as the VM: closing the viewer leaves it running,
and ~agent emacs~ again finds the same frame rather than stacking a second one.
~agent stop~ ends it.

** Changing the configuration

*** Set environment variables

One file, ~.ssh/environment~ in ~dotfilesRoot~, seeded into each sandbox like
any other dotfile and editable in place afterwards.

#+BEGIN_SRC sh
$EDITOR ~/agent-dotfiles/.ssh/environment
#+END_SRC

#+BEGIN_EXAMPLE
# Blank lines and # comments are ignored.
EDITOR=nano
VISUAL=nano
GIT_EDITOR=nano
PAGER=less
LESS=-R
#+END_EXAMPLE

Plain ~NAME=value~, one per line. No ~export~, no shell, and the value is the
rest of the line taken literally: ~$HOME~ and ~~~ stay as written, so use
absolute paths. *Do not quote.* sshd keeps the quotes as part of the value
while systemd strips them, and ~wm.service~ reads the same file — quoting is
the one way to make the two readers disagree.

~PATH~ cannot be expressed here at all, since it has to build on the value it
already has. That stays in ~/etc/profile.d/agent-path.sh~ in the image.

Why this file and not ~.profile~: sshd applies it before it execs anything, so
it lands before any shell and works whichever shell you use. Every ~agent~ verb
is an ssh command session, which is the case a shell rc file misses — see
[[*What reads it, and what does not][What reads it, and what does not]].

An edit on L0 reaches the next sandbox created, or an existing one after
~agent reset~ — see [[*Edit the dotfiles][Edit the dotfiles]]. To change a
running sandbox, edit ~~/.ssh/environment~ inside it; a new session picks that
up. Two things keep their own copy: the Emacs daemon caches its environment
for life, and ~wm.service~ reads the file at start.

#+BEGIN_SRC sh
ssh demo.agents.contained 'emacsclient -e "(kill-emacs)"'   # then: agent emacs demo
ssh demo.agents.contained 'sudo systemctl restart wm'
#+END_SRC

*** Edit the dotfiles

An edit reaches the *next* sandbox created, not the ones already running — see
[[*The agent wrapper][The agent wrapper]].

#+BEGIN_SRC sh
$EDITOR ~/agent-dotfiles/.config/emacs/init.el   # affects the next creation
agent reset demo                                 # take a fresh copy now
#+END_SRC

A sandbox is seeded from ~dotfilesRoot~ when it is created and owns its copies
from then on. There is no command to push a later change into a running one:
~reset~ is it, and it discards whatever the agent changed along the way,
because the copies and the agent's edits are on the same overlay.

For a one-off change mid-session, edit the file inside the sandbox — it is an
ordinary writable file there. Nothing propagates back to L0, and a ~reset~
discards it. The source cannot be changed from a sandbox at all: ~dotfilesRoot~
reaches the sandboxes read-only at every hop, enforced by virtiofsd on L0 and
on L1 rather than by a mount option a sandbox could undo.

*** Change a setting in site.nix

What to run afterwards depends only on what you changed, and the table says
which — see [[*Everything else, and what to re-run][Everything else, and what
to re-run]].

#+BEGIN_SRC sh
$EDITOR site.nix

nix profile upgrade agent              # credentials.*
nix run '.#deploy'                     # logging, serviceStacks, sizing, paths, extraModules
nix run 'nixpkgs#nixos-rebuild' -- switch --flake '.#agentvm' --target-host root@l1   # dns.*, ntp.*
nix run '.#golden-build'               # anything under guest.*, then agent reset per project
#+END_SRC

Pick the line that matches; they are alternatives, except for ~timezone~,
which needs both ~deploy~ and ~golden-build~. A ~guest.*~ change needs
~agent reset~ per project, since each one stays on the golden it was created
from. The settings not listed here — ~internalDomain~, ~sshIdentityFile~,
~wan.*~ and the libvirt names — need more than one command: the table says
what.

*** Change the carrier's configuration

For a change no setting covers — a package on L1, a rule of your own — write a
NixOS module in your site folder and list it in ~carrier.extraModules~. It
receives your settings as ~site~, as the stack's own modules do. ~switch~ is
quicker and keeps L1's rollback history; ~deploy~ replaces the system disk and
discards it. Neither touches ~/data~ — see
[[*Changing the carrier configuration][Changing the carrier configuration]].

#+BEGIN_SRC sh
$EDITOR carrier-local.nix              # e.g. { pkgs, ... }: { environment.systemPackages = [ pkgs.ncdu ]; }
$EDITOR site.nix                       # carrier.extraModules = [ ./carrier-local.nix ];

# in place, L1 must be running
nix run 'nixpkgs#nixos-rebuild' -- switch --flake '.#agentvm' --target-host root@l1

# wholesale: works from any state, and is what makes L1 match the flake exactly
nix run '.#deploy'
#+END_SRC

Use ~test~ rather than ~switch~ while experimenting: it activates without
becoming the boot default, so a reboot returns to the last generation that
worked. Changing what the stack's own modules do — ~carrier/network.nix~ and
its neighbours — is [[*Working on the stack itself][working on the stack
itself]].

*** Add a credential or a provider

One entry in ~site.nix~ and an upgrade. Nothing rebuilds, and the value appears
at the next attach — see [[*Adding a provider][Adding a provider]].

#+BEGIN_SRC sh
pass show ai/newprovider               # check the command prints the key alone
$EDITOR site.nix                       # one entry under credentials.entries
nix profile upgrade agent
agent start demo                       # pushes credentials without attaching
ssh demo.agents.contained 'cat /run/creds/env'
#+END_SRC

Only the first line the command prints is used, without its newline, and what
it prints on stderr is discarded: a command that prints a label before the key
puts the label into the key. With ~source = "authinfo"~ the commands are
ignored and the ~machine~ name is what finds the value.

*** Change L1 or sandbox sizing

Memory and CPU are a deploy; the data disk is not — see
[[*Everything else, and what to re-run][Everything else, and what to re-run]].

#+BEGIN_SRC sh
$EDITOR site.nix                       # l1.memoryMiB, l1.vcpu, sandbox.*
nix run '.#deploy'                     # redefines the domain; stops every sandbox
ssh l1 true && agent start demo        # once L1 is back up
#+END_SRC

~l1.dataDiskSize~ is the exception: ~install~ creates that disk only if it is
absent and never touches it again, which is what protects your state on every
later run. Growing it means resizing the file and then the filesystem inside
it, by hand.

*Untested.* The settings and the commands are proven separately; this sequence
has not been run.

*** Roll back after locking yourself out

A change that cuts ssh to L1 does not need ssh to undo: ~deploy~ works from L0
through libvirt alone — see [[*Iterating on rules][Iterating on rules]].

#+BEGIN_SRC sh
sudo virsh reboot agent-l1             # enough if the change was applied with test
$EDITOR site.nix                       # otherwise undo the change, then
nix run '.#deploy'                     # a fresh system disk from the flake
#+END_SRC

A change applied with ~test~ never became the boot default, so a reboot
returns to the last one that worked. ~deploy~ replaces L1's system disk and
with it the generation history; ~/data~ is untouched.

The serial console, ~sudo virsh console agent-l1~, is off the network, but it
asks for a login and root has no password on L1. A password set with
~ssh l1 passwd~ lives on the system disk, so it lasts until the next ~deploy~;
with one, ~nixos-rebuild switch --rollback~ from the console returns to the
previous generation.

** The image

*** Rebuild the golden, and check it

One command, then a boot on a throwaway overlay to see it come up — see
[[*Checking the golden works][Checking the golden works]].

#+BEGIN_SRC sh
nix run '.#golden-build'               # minutes for light, tens for full
ssh -t l1 golden-boot                  # ctrl-a x to quit; root, no password
agent reset demo                       # per project, to pick the new golden up
#+END_SRC

Each project stays on the golden it was created from, so the reset is what
makes the rebuild take effect. The VM ~golden-boot~ starts has no network and
cannot be reached over ssh: log in as root, with no password, on the serial
console it puts on your terminal.

*** Update the golden's Arch pin

One command does the lot: newest snapshot, the rebuild, the new date written
into ~site.nix~, then every project reset — see
[[*Updating the golden][Updating the golden]].

#+BEGIN_SRC sh
nix run '.#golden-update'
#+END_SRC

Run it when no agent is working: the reset stops every sandbox, and they stay
stopped until you start them again. Nothing is recorded or reset until the
build has succeeded, so a failed build costs no overlay and leaves ~site.nix~
as it was; the old golden, kept while the projects were pinned to it, is then
pruned. The date in ~site.nix~ is the record of what the golden contains.

*** Add a package to the image

An Arch package is one line in ~site.nix~. An AUR package is two, because it is
built under one name and installed under another — ~yay-bin~ provides ~yay~ —
see [[*The golden image][The golden image]].

#+BEGIN_SRC sh
$EDITOR site.nix        # in the guest block: extraPackages = [ "htop" ];
                        # AUR: also aurPackages = [ "foo-bin" ]; and "foo" in extraPackages
nix run '.#golden-build'
agent reset demo && ssh demo.agents.contained 'pacman -Q htop'
#+END_SRC

An AUR package left out of ~extraPackages~ is built and not installed, which
fails silently: the build succeeds and the binary is simply absent. ~makepkg~
runs on L0 with ~--syncdeps~, so a package that builds with Rust installs Rust
on L0, and leaves it there.

*Untested.* The AUR mechanism is proven by ~yay~ and ~emacs-lsp-booster~;
~extraPackages~ is checked to reach mkosi, which appends it to the image's own
list, but a build with one has not been run.

*** Switch between light and full

One setting, then the long way round: a full image is around 20 GB and tens of
minutes — see [[*The golden image][The golden image]].

#+BEGIN_SRC sh
$EDITOR site.nix                       # in the guest block: profile = "full";
nix run '.#golden-build'
agent reset demo                       # per project
agent emacs demo                       # full only; light refuses by name
#+END_SRC

Going to ~full~ adds the editor, the display stack and the document toolchain.
Going back to ~light~ removes them, so a project relying on ~agent emacs~ stops
working — the command says so rather than failing obscurely.

*Untested.* Both profiles build; switching from one to the other has not been
timed or verified end to end.

** Services, network and logs

*** Add or remove a service stack

A directory with a compose file in your site folder, an entry in ~site.nix~,
and a deploy — see [[*Adding a service][Adding a service]].

#+BEGIN_SRC sh
mkdir -p services/myservice
$EDITOR services/myservice/compose.yml # publish on $SVC_BIND, bridge svcbr-*
$EDITOR site.nix   # serviceStacks.myservice = { port = 3001; directory = ./services/myservice; };
nix run '.#deploy'
agent service list
#+END_SRC

Read [[file:services/searxng/compose.yml][services/searxng/compose.yml]] in this
repository for the conventions rather than copying the directory: its
~settings.yml~ is SearXNG's own, and a copied compose file still bind-mounts
it. Removing a stack is ~enable = false~ and another deploy, not a command —
the units are generated from that setting, so one stopped by hand comes back
at the next boot.

*** Find out why a service is unhappy

Three verbs, cheapest first — see
[[*Service stacks and MCP][Service stacks and MCP]].

#+BEGIN_SRC sh
agent service list                     # what exists, and what is running
agent service status searxng           # why the unit is unhappy
agent service logs searxng             # the last 50 lines of the unit's journal
agent service restart searxng          # a stack that is stuck; same compose file
#+END_SRC

The first start of a stack pulls images, so a minute of apparent hanging is
expected rather than a fault. A restart re-runs the compose file L1 already
has: L1 runs a copy taken when it was built, so an edited compose file, like
any ~site.nix~ change, reaches L1 only with ~nix run '.#deploy'~ or
~nixos-rebuild switch~.

*** Register an MCP server with an agent

The endpoints are declared for you in ~/etc/agent-config/mcp.json~, but no
agent reads that file: pointing one at a server is a step you take — see
[[*How agents reach it][How agents reach it]].

#+BEGIN_SRC sh
ssh demo.agents.contained \
  'CLAUDE_CONFIG_DIR=$HOME/.config/claude-api claude mcp add --scope user \
     --transport http searxng \
     "$(jq -r .mcpServers.searxng.url /etc/agent-config/mcp.json)"'

ssh demo.agents.contained \
  'CLAUDE_CONFIG_DIR=$HOME/.config/claude-api claude mcp list'
#+END_SRC

~CLAUDE_CONFIG_DIR~ is not optional: ~claude-api~ and ~claude-pro~ keep
separate config directories, and a server registered without it lands in a
third place neither session reads. Registration is on the overlay, so it
survives ~stop~ and is gone after ~reset~. For opencode it is an ~mcp~ block in
~opencode.json~ in your dotfiles.

*** Change how DNS is resolved

One setting, ~dns.resolver~ in ~site.nix~ — see
[[*The resolver, and networks that will not allow one][The resolver, and
networks that will not allow one]].

#+BEGIN_SRC sh
$EDITOR site.nix        # dns.resolver = "recursive" | "gateway" | [ "9.9.9.9@853#dns.quad9.net" ]
nix run 'nixpkgs#nixos-rebuild' -- switch --flake '.#agentvm' --target-host root@l1
ssh l1 'dig @127.0.0.1 example.com +short'
#+END_SRC

~recursive~ is the default and the right answer wherever it works: L1 walks
from the root itself, and no resolver but its own is trusted. ~gateway~
forwards to ~wan.gateway~, which is libvirt's dnsmasq on L0 and therefore
follows whatever DNS the laptop currently has — one value that is correct on
every network. A list forwards somewhere you name, and turns on DoT if every
entry carries ~@853~.

Running sandboxes survive it. Unbound restarts and its cache empties, so the
next few lookups are slower; nothing else notices. DNSSEC is validated on L1
in all three modes.

*If names have stopped resolving, ~gateway~ is the first thing to try* — see
the DNS rows under [[*If something goes wrong][If something goes wrong]] for
how to tell in two commands whether that is the problem you have.

*** Iterate on firewall rules

Edit, ~test~, and repeat: running sandboxes survive a ruleset reload, so you
can iterate against live traffic. The policy is ~carrier/network.nix~, part of
the stack, so this is done in a clone of it — see
[[*Working on the stack itself][Working on the stack itself]] and
[[*Iterating on rules][Iterating on rules]].

#+BEGIN_SRC sh
$EDITOR ~/src/agent-stack/carrier/network.nix
nix run 'nixpkgs#nixos-rebuild' -- test --flake '.#agentvm' --target-host root@l1 \
  --override-input agent-stack ~/src/agent-stack
ssh l1 'nft list ruleset | grep -n "tap-"'
# once it works: the same with switch
#+END_SRC

Until the change is in the stack your site folder uses, every later ~deploy~
or ~switch~ needs the same ~--override-input~, or it puts back the pinned
rules.

~test~ activates without becoming the boot default, so a reboot undoes it.
Taps and QEMU processes belong to ~agentctl~, not to the firewall module, so
reloading the ruleset leaves running sandboxes alone — but a change to Squid or
unbound restarts that service and drops proxied connections in flight.

*** Read the logs

Raw text on ~/data~, which survives every ~deploy~: ~ssh l1~ and grep — see
[[*Logs][Logs]].

#+BEGIN_SRC sh
ssh l1 'tail -20 /data/logs/squid/access.log'   # requests, by project name
ssh l1 'tail -20 /data/logs/unbound.log'        # who resolved what
ssh l1 'tail -20 /data/logs/flow.log'           # non-80/443, and refusals
ssh l1 'journalctl -u agent-vm@demo -n 50'      # one sandbox's unit events
ssh l1 'grep demo /data/logs/squid/access.log | tail'
#+END_SRC

The Squid log names the client as ~demo.agents.contained~ rather than an
address, so a grep for the project name yields its traffic. Hostnames are
visible because the SNI is peeked; URL paths are not, because the connection is
spliced rather than decrypted.

*** Capture a project's traffic

A pcap on that project's tap, written to ~/data/logs/pcap/~ as a size-capped
ring — see [[*Logs][Logs]].

#+BEGIN_SRC sh
agent capture demo start
# reproduce whatever you are chasing
agent capture demo stop
agent capture list                     # one row per capture: start, files, size
scp 'l1:/data/logs/pcap/demo-*.pcap*' .   # then open them in wireshark on L0
agent capture demo delete              # every capture of demo
#+END_SRC

The capture is a systemd unit rather than a command left running, so it
survives a dropped ssh connection and stops only when told to. The ring is
size-capped because an unbounded capture on a busy tap fills the data disk:
five files of 100 MB, ~demo-<start>.pcap0~ to ~.pcap4~, each gzipped once the
ring moves past it. Each ~start~ begins a new ring, so it is the number of
captures kept, not their length, that adds up.

~delete~ refuses while a capture runs: tcpdump holds its file open, so
deleting it would free nothing. ~capture list~ marks the running one, and
~(no project)~ on captures left by a project deleted before ~delete~ removed
them; those go by hand, with ~ssh l1 rm /data/logs/pcap/<name>-*.pcap*~ for a
name no other project extends.

*Untested.* The unit and the wrapper verb exist; a capture has not been taken
and opened end to end.

** Housekeeping

*** Upgrade the stack

~flake.lock~ in your site folder pins the stack's version, so nothing changes
until you ask. Moving to the newest is one command, then whatever the new
version changed:

#+BEGIN_SRC sh
cp flake.lock flake.lock.previous      # the way back: copy it over flake.lock
nix flake update agent-stack
nix run '.#deploy'                     # L1; stops running sandboxes
nix run '.#golden-build'               # the image; then agent reset per project
nix profile upgrade agent              # the wrapper
#+END_SRC

Which of the last three a version needs is in the stack's history on GitHub,
https://github.com/mclbn/agent-stack/commits. When in doubt run all three:
none touches ~/data~ or your workspaces, though the resets after
~golden-build~ discard what each sandbox installed. A setting the new version
removed fails at ~deploy~, the first command to read ~site.nix~, naming it; one
it renamed still works and prints a warning with the new name, which is the
moment to change ~site.nix~. To go back, copy ~flake.lock.previous~ over
~flake.lock~ and run the same commands again.

*** Check disk usage, and reclaim it

Naive measurement is wrong here three different ways, so use these — see
[[*Disk usage][Disk usage]].

#+BEGIN_SRC sh
# L1: the honest figure, then where it goes
ssh l1 'btrfs filesystem usage -h /data | head -12'
ssh l1 'du -shc /data/* | sort -h'
ssh l1 'du -sh /data/overlays/* 2>/dev/null'

# L0: the build tree, then reclaim it
sudo sh -c 'du -shc /var/tmp/agent-stack-golden/* 2>/dev/null | sort -h'
nix run '.#clean'                      # build scratch
nix store gc                           # store paths from past builds
#+END_SRC

If ~/data~ fills, the overlays are the place to look first: each grows with
what its agent installs, and ~agent reset~ returns one to nothing — or
~agent delete~ removes it with the rest of a project you are done with.
~nix run '.#clean' -- --all~ drops the package cache too, which costs a ~20 GB
redownload on the next build — for when the disk is actually short, not
routine.

*** Add a second project

A directory on L0 and one command. Nothing is registered anywhere first:
~agentctl~ allocates on first start, from the monotonic index in
~/data/state/alloc.jsonl~.

#+BEGIN_SRC sh
mkdir -p ~/work/otherproject           # in exportRoot; lowercase letters, digits and -
agent shell otherproject
agent list                             # the new address, above any ever used
#+END_SRC

The new sandbox gets its own uid, its own tap and its own ~/32~, and the same
policy as the first: no direct connection to L0's side of the wan segment or to
the other sandbox — see
[[*What a sandbox can and cannot reach][What a sandbox can and cannot reach]]
for what that does and does not cover. No ~deploy~, no image rebuild, and no ssh config edit: the
sandbox stanza from ~nix run '.#ssh-config'~ matches internal names by pattern, so
~otherproject.agents.contained~ resolves through L1 as the first one does.

What it costs is one overlay, which starts at kilobytes and grows with what the
agent installs. The golden is shared.

*Untested.* The allocation path is exercised daily; the second-project
walkthrough as written has not been run.

*** Delete a project

For a project you are done with. ~delete~ shuts the sandbox down if it is
running, discards everything ~reset~ discards, and then what ~reset~ keeps: the
generated configuration in ~/data/config/~, the runtime directory, the
project's captures in ~/data/logs/pcap/~, and its allocation and DNS name. No
confirmation is asked, as with ~reset~.

#+BEGIN_SRC sh
agent list                             # WORKSPACE "missing": gone from L0
agent delete old-scraper
#+END_SRC

*The workspace on L0 is never touched.* It is your data, not the stack's. As
long as it exists, any attaching verb creates the project again, under a new
address.

*The shared logs are left to rotation.* The Squid, unbound and flow logs and
the journal hold every project's lines in the same files, and age out on the
schedule in [[*Logs][Logs]]. The captures are the only per-project log, and the
only one nothing rotates, which is why they go with the project.

*The address is not reused.* The record moves to
~/data/state/alloc-deleted.jsonl~, which allocation still counts, so no other
project is ever given it. The unbound and flow logs name clients by address
alone, and this keeps every line in them attributable to the one project that
held it. The ~/16~ has room for some 65,000 projects; only tearing the carrier
down, which takes the logs with it, starts the count again.

*** Tear the whole thing down

*This destroys the carrier, every sandbox, and all the logs and state on
~/data~.* Your projects and dotfiles are untouched: they live on L0 and were
only ever mounted in. Work top-down — each step assumes the one above it.

#+BEGIN_SRC sh
# 1. the sandboxes, while L1 is still up
ssh l1 agentctl status                       # what exists
ssh l1 agentctl stop demo                    # once per project

# 2. the domain and its network
sudo virsh destroy agent-l1                  # or `shutdown` to be graceful
sudo virsh undefine agent-l1
sudo virsh net-destroy agent-wan
sudo virsh net-undefine agent-wan

# 3. the disks. l1-data.raw is the irreversible one: the golden, every
#    overlay, the logs and the allocation index are all inside it.
sudo rm -rf /var/lib/libvirt/images/agent

# 4. L0-side leftovers
nix profile remove agent
sudo rm -rf /var/tmp/agent-stack-golden      # the golden build tree
sudo rm -f /nix/var/nix/gcroots/agent-stack-virtiofsd*  # L1's virtiofsd wrappers
nix store gc                                 # store paths from past builds
#+END_SRC

Then two files of your own: the stanzas you appended to ~~/.ssh/config~ in
Quickstart step 4, between the ~--- agent-stack~ marker lines, and L1's host
key in ~~/.ssh/known_hosts~ (~ssh-keygen -R 10.99.0.2~; sandbox keys never land
there). Neither is removed for you, and nor is your site folder. The names and
the path above are the defaults: substitute yours if you changed
~domainName~, ~networkName~ or ~imageDir~.

Step 1 is not strictly required — removing the data disk takes the overlays
with it — but it shuts each sandbox down cleanly and loses nothing, so the
teardown stays reversible up to step 3.
Stopping after step 2 leaves every disk intact, and ~nix run '.#install'~
rebuilds the domain and the network from them.

*Untested.* Reasoned from what ~install~ creates, and deliberately not run:
testing it means destroying a working stack.

* Build and install the carrier

The two build commands from Quickstart step 4, with what they leave behind.

#+BEGIN_SRC sh
nix build '.#image'        # -> result/carrier.qcow2  (~10 min, builds in a VM)
nix run '.#install'        # sudo: disks, network, domain, start
#+END_SRC

~install~ is idempotent: rerunning it redefines the domain and installs a fresh
system image without touching ~/data~. A running L1 is left running, on the
old image until its next restart; ~deploy~ is the command that swaps and
restarts. One system image is retained: both
~install~ and ~deploy~ prune the older ones. Nothing
that has to survive lives on the system disk, so recovering from a bad image
means deploying a good one rather than reaching for a previous copy.

#+BEGIN_SRC sh
sudo virsh console agent-l1     # serial console; ctrl-] to detach
sudo virsh list --all
#+END_SRC

** Checking the carrier works

From L0:

#+BEGIN_SRC sh
ssh l1 true && echo "ssh ok"
#+END_SRC

Then on L1, over ~ssh l1~:

#+BEGIN_SRC sh
# disks
lsblk
findmnt /data                      # btrfs, compress=zstd, noatime
ls -la /data                       # images/ overlays/ state/ logs/ ...
lsattr -d /data/overlays           # expect the C flag

# the export root, two hops from here to a sandbox later
findmnt /srv/projects              # virtiofs
ls -la /srv/projects               # mode 0700, owner 1000, your projects listed
stat -c '%a %u:%g' /srv/projects

# nested virtualization survived host-passthrough
ls -l /dev/kvm
grep -c -E 'vmx|svm' /proc/cpuinfo    # expect one per l1.vcpu, not 0

# time and network
chronyc tracking
cat /etc/resolv.conf
ping -c1 10.99.0.1 && curl -sS -o /dev/null -w '%{http_code}\n' https://example.com
#+END_SRC

The write-through check is the one that matters for the workspace chain. On L1,
~ls~ shows uid 1000 numerically rather than as a name, which is correct: the
carrier has no operator account and never will. Create a file as that uid:

#+BEGIN_SRC sh
sudo install -o 1000 -g 1000 -m 644 /dev/null /srv/projects/demo/from-l1
#+END_SRC

and back on L0:

#+BEGIN_SRC sh
ls -l ~/work/demo/from-l1          # must show your own user, not root
#+END_SRC

Graceful lifecycle, which exercises the guest agent:

#+BEGIN_SRC sh
sudo virsh shutdown agent-l1       # should power off cleanly
sudo virsh start agent-l1
#+END_SRC

** Changing the carrier configuration

~nixos-rebuild~ is a NixOS tool and Arch does not package it, so it is run out
of nixpkgs. The ~--~ separates Nix's own arguments from the tool's. To keep it
on ~PATH~ instead: ~nix profile install 'nixpkgs#nixos-rebuild'~.

#+BEGIN_SRC sh
# configuration changes, in place, with generations and rollback on L1.
# For firewall and proxy work specifically, see "Iterating on rules" below:
# use `test` rather than `switch` while experimenting.
nix run 'nixpkgs#nixos-rebuild' -- switch --flake '.#agentvm' --target-host root@l1

# iterate on a config without touching the deployment
nix run 'nixpkgs#nixos-rebuild' -- build-vm --flake '.#agentvm' && ./result/bin/run-*-vm

# replace the system image wholesale (stops L1, swaps, restarts; /data intact)
nix run '.#deploy'
#+END_SRC

The build runs on L0 and only the closure is copied over ssh, so L1 needs
nothing installed for this. It does need to be *running*: ~switch~ reaches L1
over ssh, and a stopped carrier gives ~No route to host~.

With L1 down, or whenever what boots should match the flake exactly, use the
image path instead. It works from any state, stopping the domain first if it is
up:

#+BEGIN_SRC sh
nix run '.#deploy'
#+END_SRC

The difference is not a preference. ~deploy~ replaces the system disk, so L1's
NixOS generations and rollback history go with it — acceptable, because
nothing that has to survive lives on the system disk. That is what ~/data~ is
for. ~switch~ keeps the generations and is
far quicker for a one-line change, but leaves the system disk drifting from the
image until the next deploy.

* The golden image

Built on *L0*, not on L1: mkosi needs a conventional FHS host, and NixOS is
not one — the attempt to give it one made every pacman post-transaction hook
segfault.

This is the only part of the stack that cares which distribution L0 runs.
mkosi, ~qemu-img~ and ~rsync~ come from the flake, pinned with everything else,
but five things must come from the host: ~pacman~, which mkosi looks for inside
its own sandbox; ~mtools~, which ~systemd-repart~ uses to populate the ESP;
~makepkg~ and ~git~, which build the AUR packages; and ~curl~, which fetches the
agent installers. All but ~mtools~ are checked before the build starts, along
with ~ssh~, rather than discovered halfway through it; a missing ~mtools~ shows
only when ~systemd-repart~ reaches the ESP. They are installed as part of
[[*Requirements on L0][Requirements on L0]]; on Ubuntu, read that section's
open questions first, since four of the six are about this command.

#+BEGIN_SRC sh
nix run '.#golden-build'
#+END_SRC

It builds under ~/var/tmp/agent-stack-golden~ with sudo, converts to qcow2,
copies the result into ~/data/images/golden/~ on L1 as you rather than as root
(the stack's private key never leaves your account), repoints ~current~ only
after the copy lands, and prunes every older golden that no overlay is pinned
to (~agentctl prune~). One that is still in use is kept and named with the
projects holding it, running or not; ~agent list~ shows it in the IMAGE column
as ~(old)~, and once those projects are reset or deleted, ~agent prune~
frees it. Goldens are
named to the second, so a rebuild the same day never takes the name of one an
overlay is pinned to. The package
cache is kept so that a rebuild is cheap; the workspace and the raw image are
not.

The agents come from ~site.nix~'s ~guest.agentInstallers~, a list of vendor
installer scripts. Each is run on L0 with ~HOME~ pointed at a staging
directory, and the result is copied whole into ~/home/agent~ in the image.
Adding an agent means uncommenting the whole list in ~site.nix~ and adding a
line to it: a list you set replaces the default rather than adding to it.

They live in the agent's home rather than in ~/usr~ because these tools
auto-update and need write access to their own install directory: an update
lands on the overlay, so the image sets a floor and ~agentctl reset~ returns to
the baked version. Claude Code's native installer is built around that layout,
keeping ~~/.local/bin/claude~ as a symlink into ~~/.local/share/claude/versions/~.
npm is deliberately not used: it is deprecated for Claude Code, and an npm
global install that cannot write its own directory has auto-update disabled.

AUR packages are built by ~golden-build~ with makepkg on L0 and handed to mkosi
as a local repository, so ~yay~, and in the ~full~ profile ~emacs-lsp-booster~,
are in the golden without the image ever building anything itself. Both are
always built, whatever the profile; ~guest.aurPackages~ adds to them, and
~guest.extraPackages~ installs what was built, along with any Arch package, on
top of ~mkosi.conf~ and the profile.

~site.nix~ chooses between two images through ~guest.profile~. ~full~ is the
complete image, around 20 GB. ~light~ omits the editor,
the display stack and the document toolchain, leaving a sandbox that still
builds, runs and debugs code, uses databases and runs containers — worth having
while iterating on the stack itself, since it builds in minutes and copies to
L1 in seconds.

Console locale, keymap and timezone come from ~site.nix~ (~guest.locale~,
~guest.keymap~, and ~timezone~, which L1 shares) and default to ~en_US.UTF-8~,
~us~ and ~UTC~. A locale other than ~en_US.UTF-8~, or ~C.UTF-8~, which glibc
has built in, also needs a line in ~image/mkosi.skeleton/etc/locale.gen~ in a
clone of the stack — see [[*Working on the stack itself][Working on the stack
itself]] — since it must be generated before it can be selected. The timezone
is the exception among the three: it does not reach mkosi as its ~Timezone=~
setting, whose ~systemd-firstboot~ comes from nixpkgs and looks for zones in
NixOS's ~/etc/zoneinfo~. ~mkosi.postinst~ links
~/etc/localtime~ into the image's own ~/usr/share/zoneinfo~ instead, and fails
the build on a name that is not there.

The Arch Linux Archive pin lives in ~site.nix~ as ~guest.snapshot~ and is
passed to mkosi on the command line by ~golden-build~, so every "what goes in
the image" knob stays in one file and two rebuilds a week apart are not
silently different. ~nix run '.#golden-update'~ bumps it deliberately;
~nix run '.#latest-snapshot'~ just prints the newest available date.

** Editing the image

Changing what is in the image beyond the ~guest.*~ settings is done in a clone
of the stack and built with ~--override-input agent-stack ~/src/agent-stack~ —
see [[*Working on the stack itself][Working on the stack itself]]. There,
anything under ~image/mkosi.extra/~ is copied into the image as-is, which makes
most changes a matter of putting a file in the right place. Three mechanisms
are not obvious, and each fails silently when ignored:

- *Enabling a unit belongs in the preset file*,
  ~image/mkosi.extra/usr/lib/systemd/system-preset/00-agent.preset~. mkosi runs
  ~systemctl preset-all~ after its own install scripts, which strips any
  enablement a preset does not back — so ~systemctl enable~ in
  ~mkosi.postinst~ is undone before the image is finished.
- *~locale.gen~ belongs in the skeleton tree*, ~image/mkosi.skeleton/~, which is
  copied in before the packages install so that glibc's own hook generates the
  locale. An extra tree arrives too late.
- *Nothing executes inside the image while it is built.* Anything that has to
  run does so on L0 beforehand — the agent installers, the AUR builds — or as a
  first-boot unit inside the sandbox, which is how the pacman keyring is
  initialised.

~image/~ is staged out of the read-only Nix store into
~/var/tmp/agent-stack-golden/config~ before mkosi runs, because mkosi writes
beside its own configuration. That staged copy is what ~mkosi cat-config~
reads, and it is replaced on every build.

** Checking the golden works

Test it by booting the golden on a throwaway overlay, serial on the terminal:

#+BEGIN_SRC sh
ssh -t l1 golden-boot              # ctrl-a x to quit
#+END_SRC

If ~ctrl-a x~ does not reach QEMU, which happens when ssh or tmux swallows it,
kill it from another terminal with ~ssh l1 'pkill -f golden-test-'~, which
matches only this throwaway boot and leaves running sandboxes alone. Log in as
~root~ with no password. The VM has no network at all.

What to look for, in order, since each failure has a different cause:

| Check                                | Meaning                                                   |
|--------------------------------------+-----------------------------------------------------------|
| GRUB menu, then kernel messages      | The BIOS boot partition and grub i386-pc layout work.     |
|                                      | This is the part most likely to break.                    |
| A login prompt on the serial console | ~console=ttyS0~ reached systemd's getty generator.        |
| ~id agent~ shows uid 1000            | sysusers ran, so uid 1000 holds end to end into L2.       |
| ~ls /etc/ssl/certs~ is populated     | The certificate hook ran. Empty means agents cannot       |
|                                      | verify TLS.                                               |
| ~systemctl status agent-identity~    | Ran and exited 0, reporting no identity file. Correct:    |
|                                      | nothing mounts one yet.                                   |
| ~findmnt /work~ is absent            | Expected. ~nofail~ let the guest boot without its         |
|                                      | virtiofs tags.                                            |
| ~pacman-key --list-keys~ lists keys  | The first-boot ~pacman-init~ unit ran its keyring steps.  |
|                                      | Its last step, ~pacman -Sy~, needs the network this boot  |
|                                      | lacks, so the unit shows failed here; a real sandbox      |
|                                      | completes it.                                             |
| ~sshd~ and ~chronyd~ active          | The preset file took; preset-all did not undo it.         |
| ~systemctl list-timers~ shows fstrim | Bounds how far an overlay drifts above its real usage.    |

A golden booted this way is not reachable over ssh: it has no network, and its
sshd reads ~AuthorizedKeysFile /etc/agent-config/authorized_keys~, a mount
~agentctl~ supplies only when it starts a real sandbox. Log in over the serial
console.

** Updating the golden

The image is pinned to an Arch Linux Archive date, so rebuilding it a year from
now reproduces what was built today. Updating is one command:

#+BEGIN_SRC sh
nix run '.#golden-update'
#+END_SRC

It resolves the newest available snapshot, rebuilds against it, records it in
~site.nix~, resets every project onto the new golden, prunes the old one, and
prints how to start them again. Recording and resetting come *after* the build
on purpose: if the build fails, ~site.nix~ is unchanged and the projects keep
their overlays on the old golden. It edits the ~snapshot = "…";~ line of your
~site.nix~, which the template has; without one it says what to add.

Two things the pin does *not* cover, worth knowing before assuming a rebuild is
reproducible: the AUR packages are built from whatever the AUR has that day,
and the agent installers always fetch the current release. So a rebuild months
later gives old Arch packages with current agents. That is usually what is
wanted; to hold an agent back, point its entry in ~guest.agentInstallers~ at a
versioned installer, where its vendor offers one.

The date it writes into ~site.nix~ is the record of what the golden contains.

* Sandboxes

~agentctl~ on L1 creates a project on first start, boots it, and stops, resets
or deletes it; ~start~ is the only verb that creates one. Everything it derives
— address, uid, gid, tap — comes from one monotonic index recorded in
~/data/state/alloc.jsonl~ under ~flock~. A deleted project's record moves to
~/data/state/alloc-deleted.jsonl~ and its index is never handed out again.

#+BEGIN_SRC sh
mkdir -p ~/work/demo              # the workspace must exist first
ssh l1 agentctl start demo
ssh l1 agentctl status
#+END_SRC

The sandbox is reachable from L0 only, through L1, because that is the
direction the design allows. L1 holds no private key, so it cannot ssh in
itself:

#+BEGIN_SRC sh
ssh demo.agents.contained       # by name, through L1: see nix run '.#ssh-config'
#+END_SRC

Inside, the checks that matter:

| Check                                           | Meaning                                        |
|-------------------------------------------------+------------------------------------------------|
| ~ls /work~ shows your project files             | Two virtiofs hops, L0 to L1 to L2, are         |
|                                                 | working.                                       |
| ~touch /work/from-l2~, then check on L0         | uid 1000 end to end: it must appear owned by   |
|                                                 | you, not root.                                 |
| ~cat /etc/agent-config/identity~                | The per-project config mount arrived; this     |
|                                                 | file is the VM's identity.                     |
| ~ip addr~ shows its /32, 10.42.0.2 for the      | ~agent-identity~ read the identity file and    |
| first project (~agentctl status~ shows each)    | configured it.                                 |
| ~ping 10.42.0.1~ and ~curl https://example.com~ | The tap, the route and the masquerade work.    |
| ~getent hosts archlinux.org~                    | DNS reaches unbound on L1 and is forwarded on. |
| ~chronyc sources~                               | L1 is serving time, the only source reachable. |

Then on L1, that the isolation is real:

#+BEGIN_SRC sh
ssh l1 'ls -l /data/overlays/ /run/agent/'   # 0600 and 0700, owned by the project's uid
ssh l1 'ps -o user=,args= -C qemu-system-x86_64 | head -1'   # runs as it: 1000002 for the first
#+END_SRC

Stopping is a power button press, not a power cut, because the overlay
survives it:

#+BEGIN_SRC sh
ssh l1 agentctl stop demo
ssh l1 agentctl reset demo        # stop, then delete the overlay
ssh l1 agentctl delete demo       # reset, then drop config, captures, address
ssh l1 agentctl prune             # delete the goldens no overlay is pinned to
#+END_SRC

* The agent wrapper

One command per thing you actually want to do, run on L0. Install it once:

#+BEGIN_SRC sh
nix profile install '.#agent'
#+END_SRC

~dotfilesRoot~ was set in Quickstart step 3. Changing it later takes
~nix run '.#deploy'~, since it is part of L1's domain, and then ~agent reset~
for a project to take a fresh copy.

| Command                         | Effect                                                         |
|---------------------------------+----------------------------------------------------------------|
| ~agent claude-api <project>~    | Claude Code with the API key from tmpfs, in its own config     |
|                                 | directory; continues the last conversation in ~/work~          |
| ~agent claude-pro <project>~    | Claude Code with Pro auth; tokens live on the overlay until    |
|                                 | reset; continues the last conversation in ~/work~              |
| ~agent codex <project>~         | Codex CLI with the API key from tmpfs, ~CODEX_HOME~ on the     |
|                                 | overlay; resumes the last session in ~/work~                   |
| ~agent opencode <project>~      | opencode, keys through the environment rather than             |
|                                 | ~auth.json~; continues the last session                        |
| ~agent emacs <project>~         | ~emacsclient~ over VNC; needs the ~full~ profile               |
| ~agent vnc <project>~           | just the viewer on the sandbox's display; ~full~ only          |
| ~agent shell <project>~         | a plain shell                                                  |
| ~agent start <project>~         | bring it up and push credentials, without attaching            |
| ~agent stop <project>~          | power off, overlay intact                                      |
| ~agent reset <project>~         | stop, then delete the overlay                                  |
| ~agent delete <project>~        | reset, then free its config, captures and address; the         |
|                                 | workspace on L0 is left alone                                  |
| ~agent list~                    | every project: address, state, overlay size, golden, missing   |
|                                 | workspace                                                      |
| ~agent prune~                   | delete the goldens no overlay is pinned to; never ~current~    |
| ~agent capture <project> start~ | pcap on that project's tap; ~stop~ ends it, ~delete~ removes   |
|                                 | the project's captures                                         |
| ~agent capture list~            | every capture: project, start, files, size, running            |
| ~agent service <verb> [name]~   | the L1 service stacks: ~list~, ~status~, ~logs~, ~start~,      |
|                                 | ~stop~, ~restart~                                              |

Every terminal command — ~shell~, the two Claude verbs, ~codex~, ~opencode~ —
does the same three things: ensure the sandbox exists and runs, push
credentials, and attach inside tmux so a long run survives a dropped
connection. ~emacs~ and ~vnc~ do the first two and then open the viewer.
Dotfiles are deliberately not among them — see below.

*Both Claude verbs pick up where you left off.* A new tmux session starts
~claude --continue~, which reopens the latest conversation in ~/work~; when
there is none — the first run, or the first run after ~agent reset~ — it exits
at once and a new conversation starts instead. The fallback only fires on a
quick failure, so a continued session that ends in an error after real work
closes the pane rather than opening a fresh one. ~/clear~ inside Claude starts
a new conversation; ~/resume~ picks an older one. Reattaching to a session that
is still running does neither: tmux just attaches.

~codex~ does the same with ~codex resume --last~, which starts fresh on its own
when there is nothing to reopen. ~opencode~ asks ~opencode session list~ first
and passes ~--continue~ only when a session exists: with none, ~--continue~
shows a server error before reaching the start screen.

*Dotfiles.* ~dotfilesRoot~ is a directory on L0 — ~~/agent-dotfiles~ in the
Quickstart — exported to L1 by virtiofs and re-exported into every sandbox at
~/etc/dotfiles~, read-only at both hops. From there ~dotfiles-seed.service~ *copies* it into
~/home/agent~ the first time the sandbox boots, and never again.

Once, and then the sandbox owns them. The copies are writable, so an agent may
edit its own configuration; the edits survive ~agent stop~; nothing propagates
back to L0; and no two sandboxes can affect each other. No later boot and no
~agent~ command re-reads the mount, so a change on L0 reaches an existing
sandbox only through ~agent reset~ — which takes a fresh copy and discards the
agent's edits, since both live on the same overlay.

Layout mirrors a home directory: ~~/agent-dotfiles/.config/emacs/init.el~
becomes ~~/.config/emacs/init.el~ in the sandbox. File modes are preserved, so
an executable stays executable. ~.git/~ is skipped. ~init.el~ should load the
generated per-project fragment, which ~agentctl~ writes on L1 and mounts
read-only — see [[*The display, and Emacs][The display, and Emacs]] for what it
contains.

*Symlinks in ~dotfilesRoot~ are ignored*, and named in the sandbox's journal
rather than skipped in silence. They cannot be followed: virtiofs passes the
link text through unchanged and the sandbox resolves it against its own
filesystem, where L0's paths do not exist — so a link would be dangling there
whatever the seeding did. Dereferencing would have to happen on L0. Keep real
files in ~dotfilesRoot~, or point it at the tree the links lead to.

#+BEGIN_SRC sh
ssh demo.agents.contained 'journalctl -u dotfiles-seed'   # what was copied, and what was not
#+END_SRC

Two boundaries worth being explicit about. The mount is read-only and the
copies are not, so an agent can rewrite its own configuration inside the
sandbox and you will not see that from L0. And the source cannot be written
from below at all: both virtiofsd instances that serve it, L0's to L1 and L1's
to each sandbox, run with ~--readonly~, and L1 mounts it read-only too. A root
agent that remounts ~/etc/dotfiles~ writable still gets every write refused, so
it cannot plant anything in the files every future sandbox is seeded from.
Every sandbox can still *read* all of it, so keep nothing there you would mind
an agent seeing.

*** What reads it, and what does not

Environment variables are one of the seeded files: ~.ssh/environment~, read by
sshd because the image sets ~PermitUserEnvironment yes~. Format and examples
are under [[*Set environment variables][Set environment variables]].

sshd is the right hook because it is the only one that sees every path in.
Everything below enters the sandbox the same way — ~ssh host <command>~ — and
sshd applies the file before it execs anything, so the environment is in place
before any shell decides which of its rc files to read. That matters because
those four paths disagree:

| Path                        | What actually runs                                | Shell rc read? |
|-----------------------------+---------------------------------------------------+----------------|
| ~agent shell~               | tmux running ~exec $SHELL -l~, a login shell      | yes            |
| ~agent claude-api~,         | tmux running the agent's command line, through    | no             |
| ~claude-pro~, ~codex~,      | ~$SHELL -c "…"~                                   |                |
| ~opencode~                  |                                                   |                |
| ~agent emacs~               | ~bash -c 'agent-emacs-frame /work'~               | no             |
| a frame or subprocess of it | inherits the daemon, which inherits the above     | n/a            |

A shell rc file therefore covers exactly one of them; ~.ssh/environment~ covers
all four, and does so whichever shell you switch to.

What it does *not* reach is anything systemd starts, which is not an ssh
session at all. ~wm.service~ reads the same file explicitly through
~EnvironmentFile=~, so a program launched from i3 is covered too — any future
GUI unit wants those two lines and the ~After=dotfiles-seed.service~ that goes
with them.

*Credentials.* See [[*Credentials][Credentials]]. Briefly: they are fetched on
L0 by whatever command you name, pushed into tmpfs in the sandbox, and cleared
by ~stop~.

*Checks worth running:*

#+BEGIN_SRC sh
agent shell demo                       # attaches; ctrl-b d to detach
ssh demo.agents.contained 'ls -l /run/creds; findmnt -T /run/creds'   # tmpfs, via /run
ssh demo.agents.contained 'ls -l ~/ | head'   # dotfiles, as ordinary files
ssh l1 'findmnt /srv/dotfiles'         # the L0 export reached L1, ro
ssh demo.agents.contained 'sudo mount -o remount,rw /etc/dotfiles; sudo touch /etc/dotfiles/x'   # refused
agent stop demo && agent shell demo    # creds gone after stop, pushed again
#+END_SRC

* Network policy

unbound as the resolver, Squid intercepting 80 and 443, and an nftables
ruleset that is default-deny between segments. Together these are what a
sandbox's traffic has to pass through, and what records it. Exactly what that
allows and refuses is in the table below; it is less than the design rule, and
the gap is stated rather than left to be found.

#+BEGIN_SRC sh
ssh l1 agentctl start demo
#+END_SRC

From inside the sandbox, that ordinary work is unaffected. The name resolves
on L1 rather than on L0, which is why nothing on the laptop needs to know the
zone:

#+BEGIN_SRC sh
ssh demo.agents.contained
  getent hosts demo.agents.contained      # the internal zone resolves
  curl -sS -o /dev/null -w '%{http_code}\n' https://example.com
  sudo pacman -Syu --noconfirm           # the real test: unmodified, no proxy set
#+END_SRC

Then that the policy is enforced, from the same session:

| Check                                 | Expected                                                 |
|---------------------------------------+----------------------------------------------------------|
| ~curl --http3 https://cloudflare.com~ | Fails or falls back to TCP: UDP/443 is dropped so QUIC   |
|                                       | cannot bypass Squid.                                     |
| A public resolver on port 53          | Works, by decision: outbound DNS to the internet is      |
|                                       | permitted and appears in the flow log. A resolver on     |
|                                       | another sandbox, L0's wan side or a container is         |
|                                       | refused by segment-deny; one on your LAN is not.         |
| ~ping 10.42.0.3~ (another sandbox)    | Dropped, and logged on L1 as ~segment-deny~.             |
| ~ping 10.99.0.1~ (L0's side of wan)   | Dropped for the same reason.                             |
| ~curl http://10.99.0.1/~              | Reaches L0 if anything there listens on port 80: web     |
|                                       | traffic goes through Squid, which connects from L1 —     |
|                                       | see the table below.                                     |
| ~ssh root@10.42.0.1~ (L1)             | Refused: L1's ssh answers L0 alone.                      |
| ~curl -6 https://example.com~         | Fails: all IPv6 is dropped on the agents segment.        |

And on L1, that the traffic is visible:

#+BEGIN_SRC sh
ssh l1 'tail -20 /data/logs/squid/access.log'   # hostnames, by project name
ssh l1 'tail -20 /data/logs/unbound.log'        # who resolved what
ssh l1 'tail -20 /data/logs/flow.log'           # non-80/443, and refusals
ssh l1 'nft list ruleset | head -60'
#+END_SRC

The Squid log shows the client as ~demo.agents.contained~ rather than an
address, resolved through unbound's reverse records, so ~grep demo~ yields that
project's traffic. Hostnames are visible because the SNI is peeked; URL paths
are not, because the connection is then spliced rather than decrypted.

Containers started inside a sandbox are covered by the same rules, with no
special case: their traffic is given the sandbox's own address before it
leaves the VM, so ~docker pull~ meets exactly what everything else meets.

** What a sandbox can and cannot reach

What L1 enforces today, for a connection a sandbox opens. "Through Squid" means
L1 itself makes the connection on the sandbox's behalf, so L1's forwarding
rules never see it.

| Destination                                | Result                                        | Recorded in             |
|--------------------------------------------+-----------------------------------------------+-------------------------|
| L1: DNS (53), NTP (123), each service      | allowed                                       | unbound log, for DNS    |
| stack's port (searxng: 3000)               |                                               |                         |
| L1: any other port, ssh included           | refused                                       | —                       |
| the internet, TCP 80 and 443               | allowed, through Squid                        | Squid log               |
| the internet, UDP 443 (QUIC)               | refused; clients fall back to TCP             | —                       |
| the internet, NTP (UDP 123)                | refused: L1 is the only time source           | —                       |
| the internet, any other port, public DNS   | allowed                                       | flow log                |
| resolvers included                         |                                               |                         |
| another sandbox, L0's side of the wan      | refused, except TCP 80 and 443                | flow log, as            |
| segment (10.99.0.1), the service           |                                               | ~segment-deny~          |
| containers (172.16.0.0/12)                 |                                               |                         |
| the same, TCP 80 and 443                   | *allowed*, through Squid                      | Squid log               |
| your LAN, and L0's own address on it       | *allowed*: TCP 80 and 443 through Squid,      | Squid log, flow log     |
|                                            | everything else forwarded                     |                         |
| anything over IPv6                         | refused                                       | —                       |

The two rows in italics are the gap between this and the design rule.
Squid fetches whatever address a sandbox asks for, private ones included, and
L1's forwarding rules refuse the agents segment, the wan segment and the
container range but not the private ranges a LAN uses. So a sandbox can reach
a web server on L0 at 10.99.0.1, or on any address of L0 that answers on 80 or
443, and every port of your LAN — router, NAS, L0's own LAN address. All of it
is logged; none of it is refused. Until that changes, keep nothing listening on
L0 or on the LAN that a sandbox should not reach.

In the other direction:

| From             | To                     | Result                                                |
|------------------+------------------------+-------------------------------------------------------|
| L0               | L1                     | ssh only, from L0's address on the wan segment; sshd  |
|                  |                        | listens on L1's wan address and nowhere else          |
| L0               | a sandbox              | ssh, through L1 (~ProxyJump~); nothing direct         |
| L1               | anywhere               | allowed: L1 is trusted, and its own traffic is not    |
|                  |                        | filtered                                              |
| the containers   | the internet           | allowed; each other, between stacks, too — see        |
|                  |                        | [[*Known gaps in what exists][Known gaps in what exists]]                             |

** The resolver, and networks that will not allow one

L1 runs unbound as a *recursive* resolver by default: given ~google.fr~ it asks
a root server which servers are authoritative for ~fr.~, asks one of those
about ~google.fr.~, and asks one of those for the record. Every step is
validated against the root trust anchor, and no third party sees the whole
picture of what was asked.

*That is exactly what a transparent DNS redirect makes impossible*, and the
distinction is worth holding on to because it explains a failure that otherwise
makes no sense.

An ordinary client — your laptop, a phone, a sandbox — runs a *stub* resolver.
It sends one query with the recursion-desired bit set, meaning "you go and find
this". It does not care who receives it, so a rule that rewrites the
destination is invisible: some resolver answers, the client is satisfied. This
is why a capture on a home router works on every machine in the house.

A recursive resolver never asks that question. Each of its queries is addressed
to one specific authoritative server with recursion *not* desired, meaning
"answer only from what you are authoritative for". Redirect those to a
recursive resolver and it refuses them, correctly — it is authoritative for
nothing. Priming the root fails, so there is no second step, so every public
name fails. L1 is normally the only machine on a home network doing this, which
is why it is the only one that breaks.

The consequence is a symptom that looks like a network fault and is not:
~ping 8.8.8.8~ works, ~dig @9.9.9.9 example.com~ works, and every name fails
anyway. The second of those is the trap — it is a recursion-desired query, the
one shape an interceptor is happy to serve.

~dns.resolver~ in ~site.nix~ chooses between three ways of reaching the public
namespace. The internal zone is answered from local data before any of this and
is unaffected by all of it.

| Setting     | What it costs, and what it buys                                    |
|-------------+--------------------------------------------------------------------|
| ~recursive~ | The default, and correct wherever it works. Nothing is trusted but |
|             | the root anchor, and the queries are spread over hundreds of       |
|             | authoritative servers, so no single party sees your traffic.       |
|             | Impossible on a network that redirects port 53.                    |
| ~gateway~   | Forwards to ~wan.gateway~ — libvirt's dnsmasq on L0, which uses    |
|             | whatever resolver the laptop currently has. The address is on our  |
|             | own bridge, so this one value is portable: it means "whatever DNS  |
|             | this laptop is using", at home or in a hotel. In exchange, that    |
|             | network's resolver is in the trust path: its logging, its          |
|             | blocklists, its outages, and a complete view of what was asked.    |
| a list      | Forwards to addresses you name. With ~@853~ on every entry the     |
|             | stack turns on DoT, which is the setting for a network you do not  |
|             | trust — port 853 cannot be caught by a port-53 redirect, and you   |
|             | choose the resolver instead of inheriting it.                      |

Three things hold in every mode. The internal zone never leaves L1. The query
log is unchanged, because ~log-queries~ records what unbound was *asked*, not
how it answered — so the per-sandbox census survives forwarding intact. And
DNSSEC is validated on L1: forwarding moves where the walk happens, not who
checks the signatures. That last one has a visible consequence — a network
whose resolver strips signatures will SERVFAIL rather than resolve, which is a
correct refusal and usually means a captive portal you have not signed into.

If you forward to a resolver that serves a private zone of its own, list that
zone in ~dns.insecureDomains~. The public root proves it does not exist, and
without that entry the validator will refuse the answer.

*Untested.* ~recursive~ and ~gateway~ are both exercised. The DoT list form is
reasoned from the same mechanism and has not been run end to end.

** Iterating on rules

Rule changes are meant to be cheap, and they are: edit ~carrier/network.nix~
in your clone of the stack, then switch with ~--override-input agent-stack
~/src/agent-stack~ added — see [[*Working on the stack itself][Working on the
stack itself]]. Only the changed derivations rebuild, and nftables replaces its
ruleset atomically.

#+BEGIN_SRC sh
# while experimenting: activates without becoming the boot default, so a
# reboot returns to the last known-good generation
nix run 'nixpkgs#nixos-rebuild' -- test --flake '.#agentvm' --target-host root@l1 \
  --override-input agent-stack ~/src/agent-stack

# once it works
nix run 'nixpkgs#nixos-rebuild' -- switch --flake '.#agentvm' --target-host root@l1 \
  --override-input agent-stack ~/src/agent-stack
#+END_SRC

A rule meant for your site alone, rather than for the stack, can instead go in
a module listed in ~carrier.extraModules~ — see
[[*Change the carrier's configuration][Change the carrier's configuration]].

*Running sandboxes survive this.* Taps, routes and QEMU processes are created
by ~agentctl~, not by the firewall module, so reloading the ruleset does not
touch them. A sandbox can stay up while rules change underneath it, which is
the point: iterate against live traffic rather than against a guess.

*You cannot lock yourself out permanently.* If a rule cuts ssh from L0, a
change applied with ~test~ is undone by a reboot, and ~deploy~ rebuilds L1's
system disk from the flake without needing ssh at all — see
[[*Roll back after locking yourself out][Roll back after locking yourself out]]:

#+BEGIN_SRC sh
sudo virsh reboot agent-l1         # after `test`
nix run '.#deploy'                 # after `switch`, with the rule taken out again
#+END_SRC

To try a rule before committing to it, drive nftables directly. This is
ephemeral, and the next rebuild replaces the ruleset wholesale — which is the
point. Configuration is changed in the flake and deployed, never edited by
hand over ssh; probing is a different matter:

#+BEGIN_SRC sh
ssh l1 'nft list ruleset'
ssh l1 'nft list ruleset | grep -n "tap-\*"'
ssh l1 'nft insert rule inet nixos-fw forward-allow iifname "tap-*" tcp dport 8080 accept'   # insert: ahead of the stack's own drops
ssh l1 'nft monitor trace'         # with `nft ... meta nftrace set 1` to debug a path
#+END_SRC

One caveat: a change to Squid or unbound restarts that
service, which drops proxied connections in flight. A ~pacman -Syu~ running at
that moment fails and needs rerunning. Changes to the nftables rules alone do
not do this.

* Logs

Everything worth reading now lives on ~/data~, which survives the system-disk
replacement that every ~deploy~ performs. Raw text, no shipping, no
aggregation: ~ssh l1~ and grep.

#+BEGIN_SRC sh
ssh l1 'ls -lh /data/logs/ /data/logs/squid/'
#+END_SRC

| Where                         | What                                                             |
|-------------------------------+------------------------------------------------------------------|
| ~/data/logs/squid/access.log~ | per request: local time with its UTC offset, duration, client    |
|                               | (~demo.agents.contained~), status, bytes, method, host and       |
|                               | content type. ~/var/log/squid~ is a symlink here, which is the   |
|                               | path Squid's own configuration names                             |
| ~/data/logs/unbound.log~      | who resolved what, port 53 only                                  |
| ~/data/logs/flow.log~         | permitted non-80/443 connections, and refused cross-segment ones |
| ~/data/logs/journal/~         | unit events, QEMU, agentctl, bounded by systemd's own limits     |
| ~/data/logs/pcap/~            | captures from ~agent capture~, size-capped rings, not rotated:   |
|                               | kept until ~agent capture <p> delete~ or ~agent delete~          |

The flow log is pulled out of the kernel journal into its own file, because an
inventory is only useful if reading it does not mean wading through messages
about XSAVE features.

Retention comes from ~site.nix~'s ~logging~ block, all of it customizable:

#+BEGIN_SRC nix
logging = {
  rotate = "daily";          # how often a log turns over
  keep = 30;                 # rotations kept, so roughly a month
  maxSize = "200M";          # rotate early if one file reaches this first
  journalMaxUse = "2G";
  journalRetention = "1month";
};
#+END_SRC

Age keeps a quiet month readable; size stops a busy day filling the disk.
~maxSize~ is only evaluated when logrotate *runs*, so the timer is set to
hourly — otherwise a log could reach far past the cap before the daily run came
round. ~rotate~ still governs how often a quiet log turns over, so hourly checks
do not mean hourly rotations. The journal is bounded separately by
~SystemMaxUse~ and ~MaxRetentionSec~, systemd's own mechanism rather than
logrotate's.

Every forward rule of the stack's policy carries a ~counter~, as do the
service-stack input rules, so ~nft list ruleset~ shows packets and bytes for
each — the only way to see a drop that is not also logged, and how you tell a
rule doing work from one that has never matched.

*Checks:*

#+BEGIN_SRC sh
ssh l1 'journalctl --disk-usage; findmnt /var/log/journal'
ssh demo.agents.contained 'curl -sS -o /dev/null https://example.com'
ssh l1 'tail -3 /data/logs/squid/access.log; tail -3 /data/logs/unbound.log'
ssh demo.agents.contained 'ping -c1 -W2 10.99.0.1; true'
ssh l1 'tail -3 /data/logs/flow.log'
ssh l1 'systemctl list-timers logrotate --no-pager'
ssh l1 'logrotate --debug /etc/logrotate.conf 2>&1 | head -20'
ssh l1 'nft list ruleset | grep -E "counter packets" | head'
#+END_SRC

Then the one that matters, since it is the whole point:

#+BEGIN_SRC sh
nix run '.#deploy'                      # replaces the system disk
ssh l1 'tail -3 /data/logs/squid/access.log'   # still there
#+END_SRC

* The display, and Emacs

*Full profile only.* A light golden has no TigerVNC and no window manager; both
units carry a condition on the binary, so in a light image systemd skips them
rather than failing them, and ~agent emacs~ or ~agent vnc~ refuses by name:
/this golden has no display stack/. Set ~profile = "full"~ in the ~guest~ block
of ~site.nix~ and rebuild.

#+BEGIN_SRC sh
# the viewer, on L0: tigervnc on Arch, tigervnc-viewer on Ubuntu
agent emacs demo                      # a frame, and a viewer on it
agent vnc demo                        # just the viewer
#+END_SRC

Xvnc runs as the agent on ~:0~, bound to the sandbox's loopback with no VNC
password, and ~vncviewer -via~ tunnels to it. The gateway is the *sandbox*, not
L1: ~-localhost~ means a tunnel ending on L1 would still have to cross the
network to reach port 5900, which is the thing it forbids. ssh reaches the
sandbox through L1 anyway by the ProxyJump in ~~/.ssh/config~, so it looks like
one hop and is two. The tunnel is authenticated by key already, which is why
there is no VNC password to store anywhere.

Geometry comes from ~site.nix~, in the ~guest~ block:

#+BEGIN_SRC nix
vnc.geometry = "1920x1080";
vnc.depth = 24;
#+END_SRC

*Why VNC rather than X11 forwarding*, on an X11 host: ~ssh -Y~ is seamless but
lets the sandbox read other windows, grab the keyboard and screenshot the host
session, which contradicts the whole point. ~ssh -X~ commonly breaks the
clipboard and times out after twenty minutes. VNC is a hard boundary — the
sandbox sees a framebuffer and input events and cannot enumerate anything on
the host. Text clipboard only, and rendering is good rather than native.
~ssh -Y~ is not available either: the image's sshd sets ~X11Forwarding no~.

The window manager ships a configuration at ~/etc/i3/config~, which stops
~i3-config-wizard~ opening on first start and waiting for a keypress nobody is
there to give. It binds *Super* rather than i3's usual Alt, because Alt would
swallow every ~M-~ chord before Emacs saw it. Being the system fallback, a
~.config/i3/config~ in your dotfiles overrides it.

*The Emacs daemon's lifetime is the VM's.* It survives detaching the viewer and
dies on ~agent stop~. ~agent emacs~ is idempotent about frames: it attaches to
the one that is already there and creates one only if there is none, so
reconnecting does not stack a second frame on the first. It also points
~*scratch*~ at ~/work~, which the daemon would otherwise inherit from whatever
started it.

Closing the last frame with ~C-x C-c~ leaves the viewer open showing an empty
desktop — correct, if surprising: that kills the frame, not the X display,
which belongs to the VM and outlives any client on it. Close the viewer window
itself, or run ~agent emacs~ again for a new frame. ~agent stop~ ends
everything. Two consequences the wrapper respects: credentials are
pushed *before* the daemon first reads them, because ~auth-source~ caches a
miss and a daemon that looked too early keeps believing there is no key; and
the daemon keeps credentials in memory after the tmpfs file is gone, so the
file's lifetime bounds new reads rather than existing processes.

~init.el~ should load the generated fragment. Anywhere in the file will do,
including the very end: neither setting cares when it runs.

#+BEGIN_SRC elisp
(load "/etc/agent-config/local.el" t)   ; the t is NOERROR: absent is fine
#+END_SRC

It carries two settings, and only two. ~auth-sources~ points at the pushed
credentials, which a portable configuration has no way to know. ~custom-file~
keeps Custom's writes out of ~init.el~ — which is a writable copy, so the write
would otherwise succeed and append generated forms to configuration you
maintain on L0, where you cannot see them and ~agent reset~ discards them
without a word.

It deliberately does *not* redirect ~package-user-dir~ or the eln cache.
~~/.config/emacs/~ is an ordinary writable directory on the overlay, so the
defaults work. Packages and native-compiled output therefore live on the
overlay: they survive ~agent stop~ and are discarded by ~agent reset~, which is
what makes the first Emacs launch after a reset slow.

*Checks:*

#+BEGIN_SRC sh
ssh demo.agents.contained 'systemctl status xvnc wm --no-pager | head -12'
ssh demo.agents.contained 'DISPLAY=:0 xsetroot -solid grey30 && echo "X reachable"'
agent emacs demo
#+END_SRC

In the frame: ~M-x~ works, ~C-M-~ chords reach Emacs rather than the viewer,
and copying text moves between host and sandbox. Then close the viewer, run
~agent vnc demo~ again, and the same frame should still be there — that is the
daemon surviving disconnection, which is the point of the whole arrangement.

* Service stacks and MCP

Containers on L1, started at boot, one systemd unit per stack. Not VMs: a VM
per MCP server costs 768 MB and a boot to run three containers, and the threat
that would address — a server escaping its container — is one this design
accepts, since these are services you chose and run rather than agent-authored
code.

#+BEGIN_SRC sh
nix run '.#deploy'                     # after adding or changing one: brings it up
agent service list
agent service status searxng
#+END_SRC

The first start pulls images, so give it a minute.

| Command                        | Effect                                                          |
|--------------------------------+-----------------------------------------------------------------|
| ~agent service list~           | what exists and whether it is running                           |
| ~agent service status <name>~  | why it is unhappy                                               |
| ~agent service logs <name>~    | the last 50 lines of the unit's journal; the containers' own    |
|                                | output is ~ssh l1 docker-compose -p <name> logs~                |
| ~agent service start <name>~   | start a stack that was stopped                                  |
| ~agent service stop <name>~    | stop it until the next start or boot                            |
| ~agent service restart <name>~ | restart a stuck stack. A changed compose file needs a ~deploy~: |
|                                | L1 runs a copy taken when it was built                          |

Turning one off for good is ~enable = false~ in ~site.nix~ and a deploy, not a
command: the units are generated from that setting, so a stopped service would
otherwise come back at the next boot.

** Adding a service

A stack of your own lives in your site folder, next to ~site.nix~:

#+BEGIN_SRC sh
mkdir -p services/myservice
$EDITOR services/myservice/compose.yml    # see services/searxng/ in the stack for the conventions
$EDITOR site.nix
nix run '.#deploy'
#+END_SRC

#+BEGIN_SRC nix
serviceStacks.myservice = {
  port = 3001;                            # the one port agents may reach
  directory = ./services/myservice;       # no quotes: relative to site.nix
};
#+END_SRC

~endpoint~, what agents are told, defaults to
~http://myservice.svc.<internalDomain>:3001/mcp~; set it if the server listens
on another path.

Two substitutions the unit provides, and the compose file should use:
~$SVC_BIND~ is L1's address on the agents segment — publish there, never on
~0.0.0.0~, or the service faces whatever network the laptop is on. ~$SVC_DATA~
is a persistent directory on ~/data~, for stacks that want one.

*** The bridge name is load-bearing

Name the compose network's bridge ~svcbr-<something>~:

#+BEGIN_SRC yaml
networks:
  svc:
    driver_opts:
      com.docker.network.bridge.name: svcbr-myservice
#+END_SRC

Not cosmetic. L1's forward chain is default-deny, and Docker loads
~br_netfilter~, so traffic between containers *on the same bridge* passes
through that chain even though it is switched rather than routed. Three rules
cover every stack that follows the convention:

| Rule                        | What it allows                                                     |
|-----------------------------+--------------------------------------------------------------------|
| ~svcbr* → svcbr*~           | a stack's own containers reaching each other: the MCP server       |
|                             | calling its backend, the backend calling its cache                 |
| ~svcbr* → en*~              | the stack reaching the internet                                    |
| ~en* → svcbr*~, established | the replies                                                        |

A generated ~br-<hash>~ matches none of them. The symptom is distinctive and
misleading: names resolve, the healthcheck passes, and every connection between
containers times out.

One honest limit, since the wildcard cuts both ways: containers of *different*
stacks can also reach each other — see
[[*Known gaps in what exists][Known gaps in what exists]].

** How agents reach it

This path does not touch the forward chain at all. The container publishes on
~$SVC_BIND:<port>~, so a sandbox connecting to a service is connecting to *L1*
— an input rule, generated per service from ~port~ in ~site.nix~. Every stack
declares one, and it is the one port on L1 that agents may cross to for that
service.

unbound answers ~<name>.svc.contained~ with the same address. Containers are
not meant to be addressed directly: ~172.16/12~ is in the segment-deny set, so
an agent cannot route to a container even knowing its IP — except on ports 80
and 443, which go through Squid, and Squid connects from L1 to whatever address
it is given. See [[*What a sandbox can and cannot reach][What a sandbox can and
cannot reach]].

So adding a service needs no firewall edit: a directory with a compose file, an
entry in ~site.nix~ with ~port~ and ~directory~, and a ~svcbr-~ bridge name.

MCP servers are declared in ~/etc/agent-config/mcp.json~, written by
~agentctl~ into every project's config mount from ~serviceStacks~ in
~site.nix~:

#+BEGIN_SRC json
{ "mcpServers": { "searxng": { "type": "http", "url": "http://searxng.svc.contained:3000/mcp" } } }
#+END_SRC

The ~mcpServers~ shape is the common one, but the path is this stack's own: no
agent reads it unprompted. Each looks in its own place — Claude Code takes
user-scope servers from ~.claude.json~ in its config directory
(~$CLAUDE_CONFIG_DIR~, which ~agent~ sets per mode) and project-scope ones from
~.mcp.json~ at the project root, opencode takes an ~mcp~ block in
~opencode.json~. So the file is the single place the endpoints are declared,
and pointing an agent at them is a step you take:

#+BEGIN_SRC sh
# Claude Code, user scope — not project scope, which would write .mcp.json
# into your repository. CLAUDE_CONFIG_DIR matters: `agent claude-api` and
# `agent claude-pro` use separate config directories so their state cannot
# collide, and a server registered without it lands in a third place that
# neither session reads.
ssh demo.agents.contained \
  'CLAUDE_CONFIG_DIR=$HOME/.config/claude-api claude mcp add --scope user \
     --transport http searxng \
     "$(jq -r .mcpServers.searxng.url /etc/agent-config/mcp.json)"'
#+END_SRC

Registration lives on the overlay: it survives ~agent stop~ and is gone after
~agent reset~, so a reset means registering again. Check with ~/mcp~ inside
Claude, or:

#+BEGIN_SRC sh
ssh demo.agents.contained 'CLAUDE_CONFIG_DIR=$HOME/.config/claude-api claude mcp list'
#+END_SRC

For opencode, an ~mcp~ block in ~opencode.json~ in your dotfiles, beside the
provider configuration.

~mcp-searxng~ serves streamable HTTP, so an agent receives a URL — nothing is
spawned in the sandbox and nothing is installed in the image.

There is no authentication on that port. The published address and the firewall
are the boundary: anything that can reach it is a sandbox this stack started.

*Where a new MCP server belongs:*

| Kind of server                           | Placement                                             |
|------------------------------------------+-------------------------------------------------------|
| Local, credential-free, workspace-scoped | In the sandbox: isolating a filesystem or git MCP     |
|                                          | buys nothing, since anything it can do the agent can  |
|                                          | already do directly                                   |
| Holds credentials, or reaches services   | A service stack on L1                                 |
| Unvetted third-party code                | Its own throwaway VM, which is what a sandbox already |
|                                          | is                                                    |

* Credentials

Secrets stay on L0. At attach time the wrapper fetches only what
~site.nix~ lists, and writes two files into a tmpfs in the sandbox — so nothing
reaches the overlay or L1's disk, and ~agent stop~ clears them:

| File                  | For                                                                      |
|-----------------------+--------------------------------------------------------------------------|
| ~/run/creds/env~      | ~agent claude-api~, ~codex~ and ~opencode~, which source it when they    |
|                       | start: ~ANTHROPIC_API_KEY~ and friends                                   |
| ~/run/creds/authinfo~ | Emacs and gptel, in netrc form, mode 0600 as the netrc backend requires  |

** The default: any command that prints a secret

Each entry names a variable, the machine name it answers to, and a command run
on L0:

#+BEGIN_SRC nix
credentials = {
  source = "command";
  entries = {
    ANTHROPIC_API_KEY = {
      machine = "api.anthropic.com";
      command = "pass show ai/anthropic";
    };
  };
};
#+END_SRC

Any of these work, and they can be mixed freely between entries:

#+BEGIN_EXAMPLE
pass show ai/anthropic                        pass, GPG-backed
secret-tool lookup service anthropic          system keyring, no prompt
age -d -i ~/.age/key ~/secrets/anthropic.age  age, no GPG at all
op read op://private/anthropic/credential     1Password CLI
cat ~/.secrets/anthropic                      a 0600 file
gpg -d ~/.secrets/anthropic.gpg               GPG without netrc
#+END_EXAMPLE

Only the first line the command prints is used, without its newline; later
lines are ignored, and so is everything on stderr. Extra text on that first
line — a label before the key — becomes part of the key. Check yours before
configuring it:

#+BEGIN_SRC sh
pass show ai/anthropic | head -1       # or your equivalent
#+END_SRC

If it prompts for a passphrase, ~export GPG_TTY=$(tty)~ in your shell profile
— the wrapper keeps stdout, discards stderr and leaves the terminal alone, so
pinentry can still reach you, but gpg needs to know where. Expect one prompt
per entry while the key is locked. A command that fails shows only as
~agent: no value for VAR~; run it by hand to see why.

Note what this means for Emacs: ~/run/creds/authinfo~ is *synthesised* from
these values. gptel and ~auth-source~ work whether or not a netrc file exists
anywhere on L0.

** The alternative: one authinfo file

If you already keep secrets in a GPG-encrypted netrc — which most Emacs users
do — switch the source and the commands are ignored:

#+BEGIN_SRC nix
credentials = {
  source = "authinfo";
  authinfoFile = "~/.authinfo.gpg";
  entries = { ... };          # machine names still used; commands unused
};
#+END_SRC

Entries keep their ~machine~ names, which is how each value is found:

#+BEGIN_EXAMPLE
machine api.anthropic.com login apikey password sk-ant-...
#+END_EXAMPLE

GPG runs on L0 and nowhere else: the private key never moves, pinentry prompts
on the host, and no agent forwarding is configured.

** Either way

The entry list is the need-to-know boundary. A secret with no entry is never
fetched, so an unrelated line in your authinfo file — a mail password, a git
forge token — cannot reach a sandbox even by accident.

Adding a provider is one entry plus ~nix profile upgrade agent~. Nothing
rebuilds.

* Configuring the agents

Agent configuration belongs in ~dotfilesRoot~ on L0, laid out as it would be in
a home directory. Each sandbox is seeded with a copy when it is created and
owns it from then on, so an edit here reaches the next sandbox created; ~agent
reset~ takes a fresh copy into an existing one.

Environment variables go in ~.ssh/environment~ there, which sshd applies to
every session and ~wm.service~ reads for the display side — one file covering
both, see [[*Set environment variables][Set environment variables]].

Keys never go in these files. They arrive in ~/run/creds/env~ on tmpfs, and a
config refers to them by name, so nothing secret is ever written to the
dotfiles directory or to the overlay.

** opencode with a Zen or Go subscription

opencode's documented path for these is ~/connect~, which writes the key to
~~/.local/share/opencode/auth.json~ — on the overlay, surviving ~stop~ and
clearing only at ~reset~, which is what the credential model exists to avoid.
Reference the environment variable instead, which opencode supports directly:

#+BEGIN_SRC sh
mkdir -p ~/agent-dotfiles/.config/opencode
cat > ~/agent-dotfiles/.config/opencode/opencode.json <<'EOF'
{
  "$schema": "https://opencode.ai/config.json",
  "provider": {
    "opencode-go": { "options": { "apiKey": "{env:OPENCODE_API_KEY}" } },
    "opencode":    { "options": { "apiKey": "{env:OPENCODE_API_KEY}" } }
  },
  "model": "opencode-go/kimi-k3"
}
EOF
#+END_SRC

Zen and Go are *separate providers* sharing one key: Zen models are
~opencode/<id>~ and Go models ~opencode-go/<id>~. Declaring only one shows only
that catalogue. Run ~opencode models~ or ~/models~ for the ids your
subscription actually covers.

The ~model~ line is optional. With it, the default survives ~agent reset~,
because it comes from the dotfiles. Without it, pick with ~/models~ and
opencode remembers the choice in its state directory — which is on the overlay,
so the choice survives ~stop~ but not ~reset~.

Anthropic needs no configuration at all: opencode reads ~ANTHROPIC_API_KEY~
from the environment, so it appears alongside as a second choice.

** Adding a provider

Two edits, neither of which rebuilds anything.

1. An entry under ~credentials.entries~ in ~site.nix~: the variable name as the
   key, the ~machine~ name it answers to, and the ~command~ on L0 that prints
   the secret. Then ~nix profile upgrade agent~.
2. Make the secret reachable, which depends on ~credentials.source~:
   - ~command~ — nothing further, provided the command you named prints the
     secret on its first line.
   - ~authinfo~ — a line in the file named by ~authinfoFile~, in the usual
     shape ~machine opencode.ai login apikey password sk-...~. The ~command~ is
     ignored; the ~machine~ name is what finds the value.

The variable then appears in ~/run/creds/env~ on the next attach, and an agent
started by ~claude-api~, ~codex~ or ~opencode~ that reads it, or a config
referring to it by ~{env:VAR}~, picks it up.

* Disk usage

Three things make naive measurement wrong here, so the commands below are
chosen to avoid them. The data disk is a *sparse* file, so ~ls~ reports its
nominal size and ~du~ its real one. ~/data~ is *btrfs with compression*, so
~du~ reports uncompressed bytes and only ~btrfs filesystem usage~ knows what is
on the disk. And overlays are *qcow2 with a shared backing file*, so an
overlay's own size is its delta from the golden, not what the sandbox sees.

On L0:

#+BEGIN_SRC sh
# what the stack occupies on the laptop, real bytes rather than nominal.
# The glob runs inside sh, because the directory is 0700 root-owned and your
# shell would expand it as you, before sudo, and find nothing.
sudo ls -lrth /var/lib/libvirt/images/agent/
sudo sh -c 'du -shc /var/lib/libvirt/images/agent/* | sort -h'

# the data disk: nominal size, then high-water mark actually allocated
sudo ls -lh /var/lib/libvirt/images/agent/l1-data.raw
sudo du -h --apparent-size /var/lib/libvirt/images/agent/l1-data.raw
sudo du -h /var/lib/libvirt/images/agent/l1-data.raw

# the golden build tree, kept between builds so a rebuild is cheap
sudo sh -c 'du -shc /var/tmp/agent-stack-golden/* 2>/dev/null | sort -h'

# what the carrier image costs in the nix store, closure included
nix path-info -Sh '.#image'
#+END_SRC

Reclaiming space on L0 between builds:

#+BEGIN_SRC sh
nix run '.#clean'          # build scratch: out/, workspace/, aur/, config/
nix run '.#clean' -- --all # the package and image caches too
nix store gc               # store paths from past builds
#+END_SRC

What each holds. ~out/~ is the raw image, 41 GiB nominal and several real, and
a *failed* build leaves it behind because the conversion that normally deletes
it never ran — that is the one that fills a disk across several attempts.
~workspace/~ is mkosi scratch, ~aur/~ the cloned PKGBUILDs and their results,
~config/~ the staged copy of ~image/~ kept so ~mkosi cat-config~ can explain
what was built. ~pkgcache/~ is the downloaded packages and ~cache/~ mkosi's
incremental cache: dropping those means the next build redownloads ~20 GB, so
~--all~ is for when the disk is actually short rather than routine.

Also on L0: one dated ~l1-system-*.qcow2~ is retained in
~/var/lib/libvirt/images/agent~ — the live one, which ~install~ and ~deploy~
both prune to — and each ~golden-build~ or ~deploy~ adds store paths that only
~nix store gc~ removes.

On L1:

#+BEGIN_SRC sh
# the honest figure for the data disk: allocated, not apparent
ssh l1 'btrfs filesystem usage -h /data | head -12'
ssh l1 'df -h / /data'

# where it goes
ssh l1 'du -shc /data/* | sort -h'

# the golden, and each overlay's delta from it
ssh l1 'ls -lh /data/images/golden/; du -sh /data/overlays/* 2>/dev/null'

# what a sandbox believes it has, versus what the overlay costs and which
# golden it is pinned to. -U: a running sandbox holds the lock on its overlay
ssh l1 'for f in /data/overlays/*.qcow2; do qemu-img info -U "$f"; done'
#+END_SRC

Reading the output: a golden is retained while it is ~current~ or an overlay
is pinned to it (the IMAGE column of ~agent list~), each overlay starts at
kilobytes and grows with what the agent installs and builds, and
~agentctl reset~ returns an overlay to nothing. If ~/data~ fills, the overlays are the place to
look first, then the golden. On L0 nothing grows without being asked except the
golden build cache, which
~sudo rm -rf /var/tmp/agent-stack-golden~ reclaims at the cost of the next
build redownloading its packages.

* Working on the stack itself

Changing what the stack does, rather than how your site sets it up, happens in
a clone of this repository. Your site folder keeps its settings and builds from
the clone instead of from GitHub when told to:

#+BEGIN_SRC sh
git clone https://github.com/mclbn/agent-stack ~/src/agent-stack
$EDITOR ~/src/agent-stack/carrier/network.nix

cd ~/agent-site
nix run '.#deploy' --override-input agent-stack ~/src/agent-stack
#+END_SRC

~--override-input~ works on every command here, ~nixos-rebuild~ included, and
writes nothing to ~flake.lock~: leave it off and you are back on the pinned
version. ~golden-update~ hands the override on to the build it runs.

*A clone is a Git repository, so Nix sees only the files Git tracks.* A new
file there is invisible until ~git add~ — the single most common cause of a
confusing failure when working on the stack. Your site folder is a plain
folder and has no such rule.

~nix flake check~ in the clone evaluates everything, L1 and every command, with
placeholder settings, and builds nothing: the quick test that a change still
holds together.

** When no name resolves

Two commands on L1 separate the three things this can be. Run them in order and
stop at the first that tells you something.

#+BEGIN_SRC sh
ssh l1
dig @127.0.0.1 . NS            # can unbound prime the root at all?
dig @192.0.2.1 example.com     # TEST-NET-1. Nothing exists at this address.
#+END_SRC

| What you see                            | What it is                                     |
|-----------------------------------------+------------------------------------------------|
| Second command *returns an answer*      | Port 53 is being intercepted. Nothing exists   |
|                                         | at ~192.0.2.1~, so whatever replied is a       |
|                                         | proxy answering for every address you send to  |
|                                         | 53. Recursion cannot work here. Set            |
|                                         | ~dns.resolver = "gateway"~ and switch.         |
| First SERVFAILs, second times out       | Unbound cannot reach the roots: outbound 53 is |
|                                         | blocked rather than redirected. Same fix, or a |
|                                         | DoT list if 853 is open.                       |
| First answers, names still fail         | Not the resolver. Check ~date -u~ against      |
|                                         | reality — a clock outside the signatures'      |
|                                         | validity window fails every signed name —      |
|                                         | then ~/data/logs/unbound.log~, which now       |
|                                         | records the reason for each SERVFAIL.          |

Two things that look like evidence and are not. ~dig @9.9.9.9 example.com~
succeeding proves nothing: it is a recursion-desired query, which is precisely
what an interceptor serves happily. And ~chronyc~ reporting its pool names
unreachable is a symptom rather than a cause — chrony finds its pools through
the resolver that has just broken, which is why ~ntp.addresses~ exists.

A recursive resolver is the thing on your network most sensitive to this, so
the trigger is usually a change of network rather than a change of
configuration: a hotel, a hotspot, a new router, a VPN client that installs a
redirect on connect, or a DNS capture of your own on the LAN you came home to.

* Future improvements

Two lists. The first is things that exist but are not finished or not proven,
which is where a surprise would come from. The second is work not started.

** Known gaps in what exists

*A sandbox can reach your LAN, and web servers on private addresses.* L1's
forward rules refuse the agents segment, the wan segment and the container
range, but not the private ranges a LAN uses, and Squid fetches any address a
sandbox asks for on 80 and 443, L0's included. All of it is logged, none of it
refused — the table in [[*What a sandbox can and cannot reach][What a sandbox
can and cannot reach]] has the detail. Closing it means refusing the private,
link-local and shared ranges in the forward chain and denying private
destinations in Squid.

*L1's serial console cannot be logged into as it stands.* Root has no password
on L1, and one set by hand lives on the system disk, which every ~deploy~
replaces. Recovery does not depend on it — ~deploy~ works from L0 without ssh
— but the console is not the way back it might look like.

*The agents segment is fixed.* ~agentctl~ derives every sandbox address from
~10.42.0.0/16~, and the golden names ~10.42.0.1~ as gateway, resolver and time
source, so the segment is not a setting. It collides with nothing unless your
LAN uses 10.42.0.0/16.

*Credentials from a command are only proven against stubs.* The table parsing,
the evaluation, both output files and the skip-on-empty path all work, but
~source = "command"~ has never been run against a store that asks for a
passphrase. ~pass~ and ~gpg -d~ reach pinentry through gpg-agent, and the
wrapper keeps the first line of stdout, discards stderr and leaves the terminal
alone, so it *should* work; ~GPG_TTY~ unset is the usual reason it does not.
~source = "authinfo"~ is exercised daily.

*Three firewall rules are loaded but never exercised.* The QUIC drop needs an
HTTP/3-capable client to prove, the MSS clamp needs a reduced-MTU path, and the
IPv6 drop has never been tested because the guest has no IPv6 address to
originate from in the first place. They are believed correct and unproven.

*Service stacks are not isolated from each other by L1's firewall.* Its forward
rule matches ~svcbr*~ on both sides, so traffic from one stack's bridge to
another's is accepted there, and only Docker's own network isolation stands
between them. One rule per bridge, generated from ~site.nix~, would close it —
worth doing before running a service you trust less beside one you trust more.

*Three display checks were never run to conclusion*, and they are the ones the
arrangement exists for: that ~C-M-~ chords reach Emacs rather than the window
manager, that the clipboard crosses in both directions, and that closing the
viewer and reattaching finds the *same* frame rather than a second one.

*~/etc/agent-config~ is read-only on the guest side only.* The image's fstab
mounts it ~ro~, but ~agentctl~ serves it without ~--readonly~, so a root agent
could remount it writable and rewrite its own project's copy, which ~agentctl~
writes again at the next start. ~/etc/dotfiles~ is different: its virtiofsd
refuses writes on both hops.

*The Emacs package set is not pre-warmed*, so the first launch after a reset
compiles. Fixing it means running Emacs inside the image during the build,
which needs ~mkosi-chroot~, which the nixpkgs mkosi wrapper cannot run. The
honest options are building the golden on a host that can chroot, or accepting
the per-reset compile.

*The DoT form of ~dns.resolver~ has not been run end to end.* ~recursive~ and
~gateway~ are both exercised daily. A list of ~@853~ addresses turns on
~forward-tls-upstream~ and relies on the module's ~tls-cert-bundle~ to
authenticate the upstream; the mechanism is ordinary unbound, but if 853 is
blocked on the network you are on, the failure will look like the port-53 case
and the fix is ~gateway~.

*~internalDomain~ lives in three places*: ~site.nix~, the installed ~agent~
wrapper, and the stanzas ~nix run '.#ssh-config'~ printed into
~~/.ssh/config~. The last two are generated from the first but not kept in step
with it: a change means ~nix profile upgrade agent~ and printing the stanzas
again.

*~golden-build~ still refuses to run without ~/usr/bin/pacman~ with the message
"this must run on an Arch host".* If the Ubuntu path works, that message is
wrong and the preflight should name the missing binary instead of the
distribution.

** Not built yet

*An immutable carrier system disk*, and then a RAM-booted stateless carrier.
Both depend on the list of paths that must stay writable on ~/data~ staying
short and known. ~state/ssh/~ is on it and cannot leave: it holds L1's ssh host
key, and without it every image swap changes the carrier's identity and L0
refuses to connect.

*Egress allow-lists*, written from the logs this stack already collects rather
than guessed at in advance. The Squid access log is the raw material.

*Trust profiles*, so that not every project gets the same network policy and
the same toolchain. This is also the point at which ~agentctl~ being some 500
lines of shell should be reconsidered — it stays obviously correct today because
allocation is one ~flock~ around a lookup and an append, and every other step
is a single command. Per-project profiles are what would end that.

*Selective interception of TLS*, if it ever earns its place. Today Squid peeks
at the SNI and splices, so hostnames are logged and URL paths are not.

*The golden image on host distributions beyond Arch.* Ubuntu 24.04 is written
up in [[*Open questions on Ubuntu 24.04][Open questions on Ubuntu 24.04]] but
not yet run. Everything except the image build is distribution-agnostic
already.
